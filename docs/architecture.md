# Architecture — Yahtzee 3D

> Как строим. Решения зафиксированы в ADR (`docs/adr/`). Стек выбран на ШАГе 3.

## Стек

- **Язык:** TypeScript (строгий режим).
- **Сборка/dev:** Vite.
- **UI:** React (экраны, таблица счёта, меню, состояния).
- **3D:** Three.js через **React Three Fiber (R3F)** + helpers **drei** (тени, окружение,
  постобработка, блики).
- **Физика костей:** **Rapier** (`@react-three/rapier`) — WASM, быстрая, детерминируемая.
- **Звук:** **Howler.js** за нашим интерфейсом `SoundEngine`.
- **Состояние UI:** Zustand (лёгкий стор как «мост» между ядром и React/3D).
- **Хранилище:** `localStorage` за интерфейсом `GameStorage`.
- **Тесты:** Vitest (ядро правил/счёта покрываем модульными тестами).
- **Линт/формат:** ESLint + Prettier.

Подробности выбора — ADR 0002.

## Границы модулей (ядро / отрисовка / звук / сеть / хранилище)

Главный принцип: **ядро игры не знает ни про 3D, ни про React, ни про звук, ни про сеть.**
Оно чистое и детерминированное. Всё остальное — слои вокруг, общающиеся через контракты.

```
            ┌──────────────────────────────────────────────┐
            │                    UI (React)                 │
            │  экраны, таблица счёта, контролы, состояния   │
            └───────▲───────────────┬──────────────────────┘
                    │ читает state   │ шлёт actions
                    │                ▼
┌─────────────┐   ┌─────────────────────────────┐   ┌──────────────┐
│  render3d   │◄──┤        Transport (контракт) ├──►│   sound      │
│ Three/R3F/  │   │  Local (сейчас) / Network    │   │ SoundEngine  │
│ Rapier;     │   │  (заглушка-точка под сервер) │   │ (Howler)     │
│ показывает  │   └──────────────▲──────────────┘   └──────────────┘
│ кости       │                  │ применяет action
└─────────────┘                  ▼
                       ┌─────────────────────┐     ┌──────────────┐
                       │   core (чистый TS)  │     │ GameStorage  │
                       │ правила, счёт, RNG, │◄───►│ (localStorage)│
                       │ reducer, события    │     │ автосохранение│
                       └─────────────────────┘     └──────────────┘
```

### core/ — ядро игры (чистый TS, без DOM/3D/React)

- Типы: `GameState`, `Player`, `ScoreCard`, `Category`, `DiceState` (5 костей: значение +
  «зафиксирована»), `RollPhase` (номер броска 1..3).
- Чистые функции счёта: `scoreCategory`, `upperSum`, `totalScore` (13 категорий, верхний
  бонус +35 при ≥63, бонусные Yahtzee +100, джокер).
- **Reducer:** `reduce(state, action) => { state, events[] }` — единственный способ менять
  состояние. Детерминированно. Возвращает доменные события для слоёв (звук/сочность).
- **RNG ядра:** значения костей определяет ЯДРО (сидируемый ГПСЧ), а не физика — ради
  детерминизма и будущей сети (ADR 0004). 3D лишь красиво показывает заранее известный
  результат.

### Actions (вход в ядро)

`NEW_GAME(config)`, `ROLL`, `TOGGLE_HOLD(dieIndex)`, `SCORE(category)`.
Передача хода и конец игры выводятся ядром автоматически после `SCORE`.

### Domain events (выход из ядра, для звука/сочности)

`dice:rolled`, `dice:settled`, `die:held`, `die:released`, `score:written`,
`action:denied`, `combo:yahtzee`, `turn:changed`, `game:over`.
Слои отрисовки и звука подписываются и реагируют (звук, частицы, анимации). Ядро их только
испускает — не вызывает звук напрямую.

**Кто что испускает (уточнение, аудит ШАГ 4 п.3):**

- _Логические_ события испускает **ядро** в `reduce`: `dice:rolled`, `die:held`,
  `die:released`, `score:written`, `action:denied`, `combo:yahtzee`, `turn:changed`,
  `game:over`.
- _Тайминговое_ `dice:settled` испускает **render3d**, когда физика реально успокоилась
  (момент для звука «стук/остановка» и разблокировки UI). Без 3D (fallback) его эмитит сразу
  слой-заглушка отрисовки.

### Transport — контракт «действие/состояние» (точка под сеть)

```ts
interface Transport {
  getState(): GameState;
  dispatch(action: Action): void; // применить действие
  subscribe(cb: (s: GameState, ev: DomainEvent[]) => void): () => void;
}
```

- **LocalTransport** (сейчас): синхронно прогоняет `reduce` локально, шлёт state+events
  подписчикам, сохраняет через `GameStorage`.
- **NetworkTransport** (потом, заглушка-точка): тот же интерфейс, но `dispatch` уходит на
  сервер, а state приходит обратно. Ядро и UI не меняются. Сейчас — только пустой класс-
  заглушка с TODO, чтобы было видно точку расширения (ADR 0003).

### render3d/ — отрисовка (R3F + Rapier)

- Сцена, камера, свет, материалы стола и костей; физический бросок (тумбл) с приземлением
  на значения, заданные ядром; считывание «успокоились» → `dice:settled`.
- Частицы/блик на `combo:yahtzee`. Читает состояние, не меняет правила.

### sound/ — звук за интерфейсом

```ts
interface SoundEngine {
  play(event: SoundEvent): void;
  setMuted(m: boolean): void;
  setVolume(v: number): void; // 0..1
  startAmbient(): void;
  stopAmbient(): void;
}
```

- **Реализация (F5): процедурно на Web Audio за интерфейсом `SoundEngine`** (ADR 0006), без
  Howler/ассетов. Реальные CC0-сэмплы — позже, подменяются за тем же интерфейсом. Маппинг
  доменных событий → звуки (`sound/soundMap.ts`); настройки (mute/volume/ambient) живут в
  сторе и сохраняются в localStorage.
- **Лицензия ассетов:** когда добавим живые сэмплы — фиксировать источник + лицензию (CC0)
  в `public/sounds/CREDITS.md` и ADR. Кандидаты: archive.org CC0, freesound CC0, kenney.nl.
- **Контраст костей (аудит ШАГ 4 п.4):** на тёмном фоне Auros материал кубиков — светлый,
  точки-пипсы чёткие; проверять читаемость и контраст (доступность) при работе над F4/F6.

### storage/ — хранилище за интерфейсом

```ts
interface GameStorage {
  save(state: GameState): void;
  load(): GameState | null;
  clear(): void;
}
```

- Реализация — `localStorage` (ключ версионируется, чтобы не падать на старом формате).
  Автосохранение после каждого значимого действия; восстановление при старте; «Новая игра»
  очищает (ADR 0005).

## Контракты и события

- Единственная мутация состояния — через `reduce` (ядро). UI шлёт `Action` в `Transport`.
- Слои не зовут друг друга напрямую: связь через `Transport.subscribe` (state) и доменные
  события (реакции). Это держит границы и упрощает будущую сеть.
- Значения костей — всегда из ядра; 3D их визуализирует, не порождает.

## Стратегия заглушек (сеть)

- Контракт `Transport` готов с самого начала; используется `LocalTransport`.
- `NetworkTransport` присутствует как пустой класс с TODO и комментарием «точка под сервер»
  — реализуется в Вехе 2 без изменения ядра/UI.
- В `GameState` заранее заложены поля под будущую сеть: `gameId?`, `seed` (для общего RNG),
  `players[].id`. Это даёт патч-расширение без миграции (ADR 0003).

## Безопасность (соразмерно: чистый фронт)

- Бэкенда и секретов на старте нет.
- Единственный пользовательский ввод — имена игроков: длина ограничена, при выводе
  экранируются (React по умолчанию экранирует — не использовать `dangerouslySetInnerHTML`).
- `GameStorage` читает только свой ключ; при повреждённых данных — безопасный фолбэк на
  новую игру, без падения.

## Производительность

- Цель 60fps: число костей мало (5), физика Rapier дешёвая; следим за лишними
  React-перерисовками (3D-стейт держим вне React-рендера, через ref/Zustand-селекторы).
- Тяжёлые ассеты (звуки, окружение) грузим с прелоадером (состояние «загрузка» из spec).
- Fallback без WebGL: играбельный 2D-режим костей (минимальная отрисовка), чтобы не белый
  экран (состояние «ошибка» из spec).

## Сетевая игра (Веха 2) — план архитектуры

> Решения зафиксированы в ADR 0007–0014. Код ещё не пишется; здесь — как сеть ляжет на
> существующую структуру, НЕ переписывая ядро.

### Стек (ADR-0007)

- **Сервер:** Node.js + TypeScript на Railway. Переиспользует `core/` как общий пакет —
  одно ядро правил/счёта на клиенте и сервере.
- **Реальное время:** Socket.IO (комнаты, события, авто-reconnect). Игровой обмен — по
  сокетам + состояние комнаты в памяти сервера. Сообщения маленькие.
- **БД:** PostgreSQL (Railway), ТОЛЬКО аккаунты/статистика/лидерборд — вне горячего пути.

### Как это ложится на код (что меняется, а что нет)

```
СЕЙЧАС (hotseat):                      В СЕТИ (Веха 2):
UI → LocalTransport → core             UI → NetworkTransport ──Socket.IO──► СЕРВЕР
  (синхронно)                            (асинхронно)                          │
                                                          тот же core.reduce + секретный seed
                                                                              │
                                       UI ◄─ public state+events ◄─Socket.IO─ рассылка всем в комнате
                                              (БЕЗ seed/rng)
```

- Клиент формирует `Action` как сейчас, но `NetworkTransport.dispatch` шлёт его на сервер
  (fire-and-forget); ответ приходит **позже, асинхронно** в `subscribe`.
- Сервер — **авторитетный судья** (ADR-0009): проверяет действие (автор/комната/чей ход/
  легальность), прогоняет тот же `reduce`, рассылает **публичное состояние** (`toPublicState`,
  БЕЗ `seed`/`rng`) + события.
- **Значения костей в сети — из серверного CSPRNG** (ADR-0012), НЕ из `mulberry32(seed)`: тот
  предсказуем по выходам, поэтому прятать `seed`/`rng` необходимо, но недостаточно. Ядро принимает
  значения броска извне; локальный режим по-прежнему на сид-ГПСЧ.
- **Тайминг по протоколу** (ADR-0013): версия состояния (применять только новее), идемпотентность
  действий, `pending`-гейт кнопок, «ход применён = приход состояния» (анимация — косметика),
  `denied` — автору, события по стабильному `playerId`, ответ `room-not-found` при исчезнувшей комнате.
- У клиентов срабатывает `Transport.subscribe(...)` → UI/3D/звук реагируют как сегодня
  (кости катятся к значениям из ядра, ADR-0004).
- `LocalTransport` остаётся для соло/hotseat/офлайна (синхронный тайминг прежний).

**Честно о масштабе правок (НЕ «оживить только заглушку»):**

- `NetworkTransport` — оживает; появляется сам **сервер**.
- **`core/` ДОПОЛНЯЕМ** аккуратными чистыми функциями (без слома правил/счёта): принимать
  внешние id игроков (сейчас позиционные `p0..p3`), `isPlayersTurn`/`isGameOver`/`getResult`,
  `toPublicState`. Это расширение, не переписывание.
- **UI** учится «ждать сервер»: состояния соединения (подключаемся/ждём/разрыв) и блокировка
  кнопок на время чужого хода/броска (синхронный путь был мгновенным — сетевой нет).
- `render3d/`, `sound/`, логика/счёт ядра — не трогаем.
- Поля `gameId`, `seed`, `players[].id` под сеть уже заложены в `GameState` (ADR-0003) — без миграции.

### Аккаунты и вход (ADR-0008)

- Вход через **Google (OAuth)** — паролей не храним. Профиль: имя, аватар, статистика
  (сыграно/побед/лучший счёт), история партий.
- **Гость** — без регистрации, по коду/ссылке комнаты, временное/введённое имя; статистика
  не копится. Захотел профиль → входит через Google.
- **Несколько способов входа за единым контрактом `AuthProvider`** (ADR-0008): система не знает
  про конкретный провайдер, каждый способ реализует общий интерфейс. На старте — Google + гость;
  email и другие соцсети добавляются как новые реализации того же контракта **без переписывания**.
- Модель в БД: «пользователь» (профиль/статистика) ↔ несколько «привязок способа входа»
  (provider + внешний id) → новый способ (email/соцсеть) добавляется и привязывается к
  существующему аккаунту без миграции.

### Комнаты и путь игрока (ADR-0009)

`вход (Google или гость) → [кабинет, если зарегистрирован] → создать/войти в комнату по коду
→ собрались 2–4 → игра по сети → результат в статистику/лидерборд`. Состояние комнаты живёт
в памяти сервера; в БД идёт только ИТОГ партии.

### Отключения и реконнект (ADR-0010)

Обрыв → пауза «ждём {имя}» + таймер; возврат по ссылке/из кабинета → продолжение с того же
места; не вернулся → остальные продолжают/завершают. Точка под AI-замену вышедшего — Веха 3.

### Масштаб 300–500 (готовность без переписывания)

- Realtime — через сокеты + память; БД вне горячего пути → **узкое место не БД, а RAM/CPU
  одного процесса** (соединения + комнаты) и лимит «один процесс».
- Доращивание при росте: несколько копий сервера + **Redis** как шина между ними (комнаты
  независимы) — отдельный поздний шаг, без переписывания. На старте не делаем.

### Безопасность бэкенда (растёт vs «чистый фронт» Вехи 1)

- Секреты (ключ сессий, доступ к БД, ключи Google OAuth) — только в переменных окружения
  Railway, не в коде/гите.
- Сервер проверяет КАЖДОЕ входящее действие (автор/комната/ход/легальность); ограничение
  частоты (rate-limit) на connect / создание комнаты / вход / действия — анти-спам/бот.
- **Серверная валидация имён** (имя гостя/профиля видят другие игроки): длина, управляющие
  символы. Клиентской проверки Вехи 1 по сети недостаточно. Валидацию входных данных — общим
  контрактом (`zod`) на клиенте и сервере.
- В лидерборд — только результаты, заверенные сервером по завершённым сетевым партиям
  (не «клиент прислал свой счёт»); в рейтинг — только игры с другими людьми (анти-фарм —
  честная оговорка: ловим случайное, но не сговор двух аккаунтов; уточняется в 2.4).
- **Приватность (ADR-0008):** публично в лидерборде только имя+аватар; email/Google-id не
  публичны; удаление аккаунта закладываем сразу (анонимизация в истории партий).

### Зависимости, деплой и эксплуатация (новое в Вехе 2)

- **Зависимости (согласованы с заказчиком, делегировано):** `socket.io`/`socket.io-client`
  (realtime), `fastify` (HTTP-слой сервера), `drizzle-orm` + `pg` + `drizzle-kit` (доступ к БД
  и **миграции** схемы), `google-auth-library` (проверка Google-входа), `jose` (подпись сессий-
  токенов), `zod` (валидация). Конкретные версии — при установке. По CLAUDE.md новые зависимости
  требуют согласования — набор согласован на этом этапе.
- **Два артефакта деплоя:** клиент (статика, как сейчас) и сервер (Node на Railway) выкатываются
  раздельно. Нужны окружения **dev (localhost) ↔ prod**: адрес сервера, CORS-allowlist origin,
  redirect URI Google OAuth, домен cookie/сессии — разные per-окружение.
- **Версия протокола в рукопожатии Socket.IO:** старая вкладка против нового сервера → клиенту
  «обнови страницу», а не молчаливый рассинхрон.
- **Деплой сервера = рестарт = потеря активных партий** (состояние в памяти, ADR-0009). Для
  дружеских партий приемлемо; честно сообщаем игрокам. Аккуратный drain — улучшение позже.
- **Мониторинг с первого дня:** счётчик активных комнат/соединений в логах/метрике (узкое место —
  именно RAM/комнаты), плюс структурные логи ошибок. Иначе масштаб «вслепую».
- **OAuth deep-link:** намерение войти в комнату X сохраняется через редирект Google (классически
  теряется) — вернуть игрока в нужную комнату после входа.

### Сборка сервера и переиспользование `core` (решить ДО 2.0)

`core/` реально чистый (нет DOM/`import.meta`/Vite-специфики) — импортировать на Node можно. НО
«переиспользуем напрямую» — с оговорками, которые надо снять до кода:

- **Вторая сборочная цепочка, а не «папка».** Текущий `tsconfig.json` заточен под браузер
  (`lib: DOM`, `moduleResolution: bundler`, `allowImportingTsExtensions`, `noEmit`) и `include: ["src"]`
  — `server/` он не видит и для Node не годится. Нужен отдельный `tsconfig.server.json` + реальный
  серверный раннер/сборка (**tsx** для dev, **tsup/esbuild** для prod-эмита). Выбрать до 2.0.
- **ESM без расширений.** Импорты в `core` (`from './scoring'`) дорезолвивает бандлер; голый Node-ESM
  требует `.js`. Значит сервер тоже идёт через транспайлер/бандлер (tsx/tsup), а не `node` напрямую.
- **Окружение:** зафиксировать `engines.node` (+ `.nvmrc`) — «у меня собирается» ≠ Railway. Dev — два
  процесса (`vite` + watch-сервер, напр. `concurrently`) с проксированием Socket.IO. Миграции на
  Railway (`drizzle-kit`) — явный шаг деплоя (не «как-нибудь при старте»), схема живёт в `server/platform`.

### Режимы игры, точка входа и хранилище (ADR-0014)

- **Явная развилка «локально (hotseat/соло) vs по сети».** Сейчас роутер (`App.tsx`) переключает
  экраны только по состоянию игры — нет меню/режима. Веха 2 добавляет меню + экраны лобби/кабинета/
  лидерборда поверх Start/Game/Winner; `Transport` выбирается режимом (`Local` vs `Network`).
- **Хранилище разведено:** `GameStorage` (localStorage, ADR-0005) — ТОЛЬКО локальные партии. Сетевая
  партия живёт на сервере (ADR-0009), localStorage её не сохраняет/не восстанавливает (иначе
  перезагрузка поднимет устаревшую копию поверх сетевого реконнекта).
- **«Play again»/реванш — по режиму:** локально `newGame`; в сети — на сервере (комната жива после
  `game:over`). WinnerScreen разводит кнопку по режиму сразу.
- **Соло-рекорд (обещание spec) — локальный персональный рекорд** в `GameStorage` (лучший итог между
  сессиями, без аккаунта/сети). Сетевая статистика/лидерборд — отдельно, для зарегистрированных.

### Платформа vs игра (задел под будущий портал, ADR-0011)

Сетевую часть строим как **переиспользуемую платформу**, отделённую от конкретики Yahtzee, —
с прицелом на будущий портал из нескольких игр (Веха 4+). Yahtzee — ПЕРВЫЙ «модуль игры» на
этой платформе. **Без оверинжиниринга:** реализуем только нужное Yahtzee, но с чистым швом,
чтобы платформу можно было выделить в отдельный пакет под вторую игру.

**Что в платформе (игро-НЕзависимое, переиспользуемое):**
сервер (Node + Socket.IO), соединения; комнаты (создание/вход по коду, хозяин, список игроков,
статусы); авторизация (Google + гость) и сессии; кабинеты (имя, аватар); инфраструктура
лидерборда (механизм общий — очки пер-игровые); реконнект/пауза; авторитетный цикл
«принять действие → проверить (автор/комната/ход) → прогнать `reduce` игры → разослать
состояние+события»; хранение ОБОБЩЁННОГО итога партии.

**Что в игре (игро-специфичное):** правила и счёт (`core`/`reduce`), типы `Action`/`GameState`/
`DomainEvent`, 3D-отрисовка, звук; маппинг конца партии в обобщённый «результат».

**Граница = контракт `GameModule`** (совпадает по духу с `Transport`, ADR-0003): платформа
вызывает его «вслепую», игра реализует.

```ts
interface GameModule<State, PublicState, Action, Event, Result> {
  createInitialState(playerIds: string[], config, seed): State; // id мест задаёт платформа
  reduce(state, action): { state: State; events: Event[] };
  isPlayersTurn(state, playerId): boolean; // авторизация действия на сервере
  isGameOver(state): boolean;
  getResult(state): Result; // обобщённый итог → статистика/лидерборд
  toPublicState(state, forPlayerId?): PublicState; // снять секреты (seed/rng) перед рассылкой
}
```

`toPublicState` живёт в игре (только игра знает свои секреты) и обязателен для анти-чита
(ADR-0009): сервер рассылает клиентам именно публичное состояние. В сетевом режиме случайность
(значения костей) платформа подаёт В игру извне — из серверного CSPRNG (ADR-0012), а не игра
выводит её из seed; `reduce`/`ROLL` принимает готовые значения. Новая игра «получает сеть
бесплатно», реализовав `GameModule` (+ свой клиент-рендер): комнаты, аккаунты, лидерборд,
реконнект даёт платформа.

**Раскладка папок под лёгкое выделение** (моно-репо, без преждевременного дробления на
публикуемые пакеты — это рефакторинг Вехи 4+):

```
src/
  core/            игро-специфичное ЯДРО Yahtzee (есть сейчас) — реализует GameModule
  transport/       Transport-контракт + Local/Network (есть сейчас) — клиентский шов
  render3d/, ui/, sound/   игро-специфичное (есть сейчас)
  platform/        НОВОЕ, игро-НЕзависимое — клиентская часть платформы
                   (лобби/комнаты/вход/кабинет/лидерборд UI + сетевой клиент)
server/            НОВОЕ — серверная платформа (Socket.IO, комнаты, auth, сессии, БД,
  platform/        авторитетный цикл) — игро-НЕзависимое
  games/yahtzee/   тонкая обвязка: подключает core Yahtzee как GameModule к платформе
```

При появлении 2-й игры `server/platform` и `src/platform` выносятся в пакет, а `core/` каждой
игры остаётся при ней. Сейчас это просто директории с ясной границей, не отдельные пакеты.
