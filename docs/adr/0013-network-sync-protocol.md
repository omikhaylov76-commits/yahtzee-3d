# ADR 0013 — Сетевой протокол синхронизации (версии, идемпотентность, фазы хода)

- Статус: accepted
- Дата: 2026-06-18

## Контекст

Аудит распределённой корректности нашёл в плане Вехи 2 несколько гонок и рассинхронов:
переупорядочивание/дубли сообщений Socket.IO, асинхронный `dispatch` против синхронного UI
(двойные действия), разблокировка UI по ЛОКАЛЬНОЙ анимации костей, отсутствие маркера «к какому
ходу относится действие», неадресные ошибки и неопределённый ответ при «комната исчезла».
Нужен явный контракт сетевого обмена, иначе клиенты разъедутся.

## Решение

- **Версия состояния.** Каждое публичное состояние несёт монотонный `stateVersion` (счётчик на
  комнату). Клиент применяет входящее состояние, ТОЛЬКО если `version > текущей`; иначе игнор.
  Это разом лечит переупорядочивание, дубли и «хвост» старых апдейтов после реконнекта.
- **Идемпотентность действий.** Действие клиента несёт `actionId` (или `forVersion`/`turnId`).
  Сервер применяет действие строго последовательно на комнату и отвергает повтор/устаревшее
  (`stale`). Защищает от дублей Socket.IO и replay.
- **In-flight гейт на клиенте.** Транспорт держит флаг `pending` (поднят при `dispatch`, снят при
  приходе соответствующего состояния). Кнопки блокируются и по `pending`, а не только по уже
  применённому состоянию — иначе двойной Roll/Score до ответа сервера.
- **«Ход применён» = приход авторитетного состояния**, НЕ локальный `dice:settled`. Анимация костей
  (`settling` в render3d) — чисто косметика, «догоняет» состояние. Фазы броска (rolling → committed
  → settled) задаёт сервер; запись счёта/смена хода гейтятся серверным состоянием, а не FPS клиента.
- **Адресность сообщений.** `action:denied` идёт ТОЛЬКО автору (unicast), не в общий поток комнаты.
  События наружу транслируются по СТАБИЛЬНОМУ `playerId`, а не по позиционному индексу (индекс
  ненадёжен при реконнектах/выходах).
- **Протокольные ответы реконнекта.** На реконнект к неизвестной/истёкшей комнате сервер отвечает
  явным `room-not-found`/`expired` → клиент показывает «партия завершена», а не вечную загрузку
  (в т.ч. после деплоя/рестарта сервера, ADR-0009).
- **Версия протокола в рукопожатии** (Socket.IO handshake) — граница безопасности: несовпадение →
  «обнови страницу», действия НЕ обрабатываются (reject, не downgrade).
- **Доставка событий привязана к версии состояния** (события приходят вместе со state своей версии),
  чтобы одиночные звуковые/визуальные события (`combo:yahtzee`) не терялись между апдейтами.

## Альтернативы

- **Доверять порядку Socket.IO без версий:** Socket.IO не гарантирует порядок при реконнекте/
  нескольких неймспейсах — отклонено.
- **Оптимистичные апдейы на клиенте (применять до сервера):** сложно откатывать при расхождении с
  авторитетом; для пошаговой игры не нужно — отклонено (хватает `pending`-гейта).

## Последствия

- ➕ Устойчивость к переупорядочиванию/дублям/потере пакетов; реконнект догоняет состояние снимком.
- ➕ Нет двойных действий; UI честно «ждёт сервер».
- ➕ Чужой бросок проигрывается без рассинхрона; запись не «в полёте».
- ➖ Публичное состояние и действия обрастают служебными полями (`stateVersion`, `actionId`).
- ➖ Клиентский транспорт сложнее (кэш состояния, pending, отбраковка устаревшего) — это и есть
  основной объём «оживить `NetworkTransport`».
