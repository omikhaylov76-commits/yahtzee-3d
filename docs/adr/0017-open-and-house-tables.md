# ADR 0017 — Открытые и дежурные столы + публичный список (вход без кода)

- Статус: accepted
- Дата: 2026-06-20

## Контекст

Сейчас весь онлайн — приватный: комната = секретный 6-символьный код (он же ключ реестра),
`/status` намеренно не отдаёт коды/имена («код = пропуск», 2.P.2). Заказчик хочет ещё две
двери: **открытый** стол игрока (виден всем, вход без кода) и несколько постоянных «дежурных»
столов сервера. Аудит подтвердил: публичный вход через код-механизм невозможен (`isValidCode`
требует ровно 6 Crockford-символов; `house-1` нормализуется в невалидный код), а анти-перебор
кода (`failJoin`) залочит честного игрока при кликах по устаревающему списку.

## Решение

1. **Три типа комнаты — поле `Room.visibility: 'private' | 'open' | 'persistent'`** (одно поле,
   без подклассов/отдельных реестров). `private` — как сейчас (по коду, не в списке). `open` —
   создаёт игрок, виден в списке, вход без кода. `persistent` — дежурные столы сервера, не
   удаляются, после партии возвращаются в лобби (ADR-0016).
2. **5 дежурных столов** создаются при старте сервера со стабильными id (`house-1`..`house-5`,
   ВНЕ Crockford-пространства кодов) и тематическими названиями (морская тема в тон Auros):
   **Tide Table, Coral Reef, The Lagoon, Deep Current, The Abyss**. Исключены из уборки мусора
   и из лимита `MAX_ROOMS` (в ОБЕИХ ветках). Создание идемпотентно; инвариант «sweeper не трогает
   `persistent`» закрыт тестом.
3. **Публичный список — HTTP `GET /tables`** (не realtime-стрим): отдаёт ТОЛЬКО
   `{tableId, title, count, capacity, status}` для `visibility!=='private'` — **без имён игроков
   и без кодов**. Клиент опрашивает раз в несколько секунд, пока открыт экран. Та же планка
   приватности, что у `/status`.
4. **Отдельный путь входа `joinOpen` по `tableId`** из списка: НЕ через
   `normalizeCode`/`isValidCode`, НЕ инкрементит `failJoin` (для публичного входа перебор
   бессмыслен — список и так открыт). Гейт ника применяется (ADR-0015). Название открытого стола
   задаёт владелец; чистится общим `normalizeName` (XSS/невидимки/длина).
5. **Клиент — отдельный слой списка.** Лёгкий стор + экран `tables` (новый `view`), НЕ внутри
   игрового `Transport`/`gameStore.mode`/`OnlineStatus` (иначе ломается create/join/invite и
   игровой гейтинг кнопок). Статусы списка (`loading/ready/empty/error`) — отдельный тип. Клик по
   столу = тот же гейт ника → `joinOpen`. «Try again»/«Leave» возвращают в список, если игрок
   пришёл оттуда (`onlineReturn`). Stale-клик (стол заполнился/стартовал/исчез) — ШТАТНЫЙ путь:
   тихий refresh + тост, без штрафа. Опрос с правильным жизненным циклом (стоп на unmount/при
   уходе в игру, пауза на скрытой вкладке, отмена in-flight) — это НОВЫЙ паттерн в проекте.
6. **Модерация залипших — обязательна** (не «потом»): без хозяина в открытом/дежурном столе
   тролля не выгнать, а залипший блокирует старт. Закрывается авто-освобождением молчащего места
   (ADR-0016, предохранитель А).

## Альтернативы

- **Публичные столы по тому же коду:** код «засветится» как секрет, сломается
  `isValidCode`/анти-перебор. Отклонено — отдельный публичный id и путь входа.
- **Realtime-стрим списка (push при изменении):** избыточно для пилота. Отклонено — HTTP-опрос
  (как `/status`).
- **Список внутри игрового стора/транспорта:** регрессия create/join/invite и игрового
  гейтинга. Отклонено — отдельный слой.

## Последствия

- ➕ Три понятные двери; экран-список никогда не пустой (5 дежурных всегда есть).
- ➕ Переиспользуем готовые компоненты Auros (`.seat`/`.conn-status`/`.count-seg`/`.pip`);
  нового CSS минимум (бейджи READY/House, чип «in game», 2-колоночный сегмент, тост).
- ➖ **Анти-накрутка лидерборда (2.4.a) — жёсткая зависимость:** дежурный стол позволяет одной
  паре сыграть реванш-серию и нафармить → рейтинг нельзя включать до защиты. Зафиксировано в
  roadmap.
- ➖ Модерация открытых столов на старте минимальная (авто-освобождение залипших + фильтр имён);
  кик-хозяином в открытых нет — кандидат в backlog/2.4.
- ➖ Новый паттерн опроса на клиенте (жизненный цикл интервала) — прецедента в проекте не было.
