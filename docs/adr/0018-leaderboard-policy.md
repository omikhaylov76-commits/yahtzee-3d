# ADR 0018 — Политика лидерборда + принцип no-pay-to-win

- Статус: accepted
- Дата: 2026-06-21

## Контекст

Веха 2, фича 2.4.a — публичный лидерборд. Данные уже пишутся с 2.3.d (`matches` с
`registeredCount`, `match_players` с `userId`/`total`/`isWinner`, индекс по `userId`). Нужно
зафиксировать ПОЛИТИКУ зачёта (что попадает в рейтинг), метрику ранжирования, приватность и
принцип монетизации (CLAUDE.md/roadmap: «оформить мини-ADR при старте лидерборда»). Аудит 2.5
пометил анти-фарм реванш-серий как ЖЁСТКУЮ зависимость лидерборда.

## Решение

1. **В зачёт — только «честные» партии:** СЕТЕВЫЕ, естественно завершённые (`game:over`), с
   **≥2 РАЗНЫМИ зарегистрированными** игроками (`matches.registeredCount >= 2`). Гостевые места,
   локальные партии, брошенные/прерванные/forfeited — НЕ в рейтинг (брошенные вообще не пишутся,
   2.3.d). Это уже выражено индексируемым полем `registeredCount` — пересчёт не нужен.
2. **Метрика ранжирования — СУММА очков** игрока за все зачётные партии (решение заказчика
   2026-06-21). Строка лидерборда богатая (показываем больше, чем сортируем): **ник+аватар ·
   очки (сумма) · лучшая игра (max) · сыграно (count) · победы (count где `isWinner`)**. Один
   SQL-агрегат по `match_players` (как `getPlayerStats`, но кросс-юзерно). Сортировка по сумме
   очков; смена сортировки/кликабельные колонки — возможное улучшение позже.
3. **Только не-удалённые игроки с ником.** Удалённый аккаунт (tombstone `users.deletedAt`) в
   лидерборде НЕ показывается (PII затёрт, ник освобождён); но его прошлое участие УЖЕ учтено в
   `registeredCount` чужих партий (честность рейтинга соперников сохраняется).
4. **Приватность:** публично — ТОЛЬКО ник + аватар + агрегатные метрики. Никаких email/Google-id,
   никаких кодов комнат, никаких имён гостей. (Та же планка, что `/status` и `/tables`.)
5. **Анти-фарм — мягко для пилота (осознанный риск).** Базовый фильтр (≥2 разных
   зарегистрированных) ловит случайное и гостевое, но НЕ защищает от двух сговорившихся аккаунтов,
   гоняющих реванш-серии на дежурном столе (вектор из аудита 2.5). Для дружеского пилота риск
   ПРИНЯТ и честно задокументирован; строгая защита (кулдаун зачёта повторных встреч одной пары,
   детект сговора, уникальность по IP/identity) — отдельная задача позже (backlog), ДО широкого
   запуска.
6. **No-pay-to-win (принцип монетизации, РЕШЕНО заказчиком, фиксируем здесь).** Монетизируем
   красоту и удобство (скины костей, темы стола, премиум-хост, косметика), НИКОГДА — игровое
   преимущество: иначе рушится честный лидерборд (авторитетный сервер — единственный источник
   правды о счёте). Поля-крючки `users.tier`/`users.entitlements` уже заложены (2.3.a) — пустые
   полки под косметику без миграции.

## Альтернативы

- **Ранжировать по победам / % побед** (с минимумом игр) — отклонено в пользу суммы очков (выбор
  заказчика; награждает и результат, и активность). Колонки победы/% всё равно показываем.
- **Строгий анти-фарм сразу** (кулдаун пар/детект сговора) — отклонено для пилота (сложно, дольше;
  дружеский масштаб риск терпит) → backlog.
- **Показывать удалённых как «Deleted player»** — отклонено (бессмысленно и шумно в публичной
  витрине; tombstone именно скрывает PII).

## Последствия

- ➕ Модель БД уже готова (2.3.d) — лидерборд это запрос + экран + политика, без миграции.
- ➕ Приватность и честность зачёта зафиксированы единообразно с остальной платформой.
- ➕ No-pay-to-win зафиксирован ДО появления монетизации — решения не загонят в угол.
- ➖ Сумма очков как метрика поощряет активность (больше партий → больше суммы); для пилота ок,
  при желании позже добавить альтернативные сортировки.
- ➖ Анти-фарм мягкий — рейтинг пилота не защищён от сговора друзей; нельзя выдавать за
  «соревновательный» до строгой защиты (backlog, отмечено в roadmap как зависимость).
