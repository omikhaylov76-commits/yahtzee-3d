# ADR 0015 — Уникальный игровой ник (отдельная личность в игре)

- Статус: accepted
- Дата: 2026-06-20

## Контекст

В кабинете (2.3.e) игроку нужна управляемая игровая личность. Имя из Google — это «настоящее
имя» аккаунта: может быть «Имя Фамилия», совпадать у разных людей, меняться на стороне Google.
Заказчик хочет, чтобы игрок САМ придумывал и редактировал свой игровой ник и чтобы ник был
УНИКАЛЬНЫМ — узнаваемая личность в игре/истории/лидерборде, без двух одинаковых.

ADR-0008 описал вход и модель «пользователь ↔ привязки входа», но НЕ вводил отдельный уникальный
ник (там профиль = «имя, аватар», имя бралось из Google). Это решение дополняет ADR-0008.

## Решение

- **Ник — отдельное поле аккаунта**, независимое от Google-имени. Google-имя сохраняем как
  справочное «настоящее имя»/fallback; в игре, истории партий и лидерборде показываем НИК.
- **Уникальность — глобальная, без учёта регистра** (и невидимых/пробельных различий): ключ
  уникальности = свёрнутая форма (`normalizeName` + lower/casefold). «Alex» и «alex» — один ник.
  Гонку (двое берут ник одновременно) ловит UNIQUE-ограничение БД → второму «ник занят». Истина —
  ограничение БД при сохранении (а не предварительная проверка: избегаем TOCTOU). «Проверка
  доступности» при вводе — опциональный UX-бонус, не гарантия.
- **Ник обязателен для зарегистрированного игрока.** При первом входе — лёгкий онбординг
  «придумай ник»; до выбора ника зарегистрированный не допускается в сетевую игру. Локальная
  игра/гость ника не требуют (у гостя — временное/введённое имя, как в 2.2.b).
- **Правила ника (мягкие, как имя 2.2.b):** общая чистая функция `shared/names` (`normalizeName`,
  ≤20 кодпойнтов, без управляющих/zero-width/bidi/`<>`), плюс минимальная длина и набор
  ЗАРЕЗЕРВИРОВАННЫХ имён («Deleted player» и пр. системные) — занять нельзя (сверка по тому же ключу).
- **Снимок ника в истории.** В `match_players.display_name` пишем ник на момент партии (как уже
  решено в 2.3.d) — смена ника не переписывает прошлые партии.
- **Освобождение при удалении аккаунта.** Tombstone (2.3.e) освобождает ник (ключ уникальности →
  NULL; в Postgres несколько NULL не конфликтуют) — освободившийся ник может занять другой.

## Приватность при удалении (уточняет ADR-0008)

Историю партий впервые читает кабинет (2.3.e), далее лидерборд (2.4). Чтобы «удалил — значит
удалил» работало по факту, при удалении PII затираем ФИЗИЧЕСКИ: в `users` (ник/имя/аватар
обезличены) И в снимках его строк `match_players.display_name` → «Deleted player». `user_id` в
истории СОХРАНЯЕМ (партия остаётся «честной» для рейтинга 2.4), привязки входа (`identities`)
удаляем (повторный вход Google = новый аккаунт), сессии отзываем (`tokenVersion++`). Так читателям
истории не нужен хрупкий «обязательный join на deleted_at» — личных данных в строках просто нет.
Всё одной транзакцией.

## Альтернативы

- **Редактировать Google-имя напрямую, ники не уникальны** (раннее предложение) — проще, но нет
  узнаваемой уникальной личности; отклонено заказчиком.
- **Уникальность по сырой строке (с регистром)** — «Alex/alex/ALEX» как разные → путаница и
  имперсонация; отклонено.
- **Прятать имя удалённого join'ом на deleted_at, снимок оставить** — снимок цел, но реальное имя
  остаётся в БД (PII), и каждый будущий читатель ОБЯЗАН join'ить (хрупко); отклонено в пользу затирания.

## Последствия

- ➕ Узнаваемая уникальная личность; смена ника не ломает историю (снимки).
- ➕ Настоящее удаление PII; читатели истории/лидерборда не несут риск утечки.
- ➖ Новое поле + ключ уникальности → миграция БД (Railway, аддитивно, с подтверждением).
- ➖ Обязательный ник = онбординг при первом входе + гейт перед сетевой игрой (небольшой UI).
- Email/пароль как ещё один способ входа — по-прежнему открыт (ADR-0008), здесь не меняется.
