# ADR 0009 — Модель комнат и авторитетный сервер (переиспользование ядра)

- Статус: accepted
- Дата: 2026-06-18

## Контекст

Сетевая игра идёт «по комнатам»: игрок создаёт комнату → получает код/ссылку → друзья
заходят (зарегистрированные или гости) → собрались 2–4 → старт. Кости и счёт должны
считаться честно (анти-чит). Ядро (`core/`) уже детерминированное и авторитетно по значениям
костей (ADR-0004), а слои общаются с игрой через контракт `Transport` (ADR-0003), где
`NetworkTransport` — готовая заглушка.

## Решение

- **Сервер — авторитетный судья.** Он держит состояние каждой активной комнаты в памяти и
  прогоняет **тот же `core.reduce`** со своим секретным `seed`. Значения костей и счёт
  рождаются на сервере; клиенты только проигрывают результат (кости катятся к значениям из
  ядра, ADR-0004). Подделать с клиента нечего.
- **Ядро — общий пакет, его ДОПОЛНЯЕМ (не переписываем).** `core/` переиспользуется и на
  клиенте, и на сервере. Но для сети ядру нужны небольшие ЧИСТЫЕ добавления (без слома правил):
  принимать **готовые id игроков от сервера** (сейчас `createGame` ставит позиционные `p0..p3` —
  серверу нужны стабильные id, привязанные к сессии/аккаунту); публичные функции `isPlayersTurn`,
  `isGameOver`, `getResult`; проекция **публичного состояния** (см. ниже). Это аккуратные
  расширения, а не переписывание логики/счёта.
- **⚠️ Публичное состояние без секретов (анти-чит).** `GameState` содержит `seed` и `rng`
  (состояние генератора) — по ним клиент мог бы ПРЕДВЫЧИСЛИТЬ будущие броски. Поэтому сервер
  рассылает клиентам **урезанное публичное состояние** (`toPublicState`) БЕЗ `seed`/`rng`.
  Полное состояние с генератором живёт только на сервере. Без этого авторитетность бессмысленна.
- **Клиент — через `NetworkTransport`. Тайминг становится АСИНХРОННЫМ.** UI как и сейчас
  формирует `Action`, но `dispatch` лишь отправляет его на сервер по Socket.IO (fire-and-forget);
  новое (публичное) состояние и события приходят ПОЗЖЕ, асинхронно, в `subscribe(...)`. В отличие
  от `LocalTransport` (синхронно: dispatch → сразу состояние), UI должен уметь «ждать сервер»:
  состояния соединения (подключаемся/ждём ответ/разрыв) и аккуратная блокировка кнопок на время
  чужого хода/броска. `LocalTransport` остаётся для соло/hotseat/офлайна (там тайминг прежний).
- **Комнаты:** короткий код/ссылка; роли (хозяин комнаты), список игроков, статус
  (ожидание/идёт/завершена). Поля `gameId`, `seed`, `players[].id` под это уже заложены в
  `GameState` (ADR-0003) — без миграции.
- **Создание партии — через `createInitialState` на сервере, НЕ через action `NEW_GAME`.**
  В ядре есть два пути появления игры (`NEW_GAME` в reduce и прямое создание); сервер использует
  прямое создание со своим seed и готовыми id игроков. `NEW_GAME` остаётся для локального режима.
- **Сервер проверяет каждое действие:** автор, его ли комната, его ли сейчас ход, легально ли
  действие (**схема `zod` на КАЖДЫЙ action**, не только имена — напр. `TOGGLE_HOLD` индекс 0..4).
  Нелегальное отклоняется (`action:denied`, unicast автору, ADR-0013).

### Жёсткие требования по аудиту (заложить ДО кода)

- **Источник значений костей — серверный CSPRNG, не `mulberry32(seed)`** (ADR-0012): иначе броски
  предсказуемы по выходам. `seed` в сетевом пути — без дефолта.
- **Протокол синхронизации** (ADR-0013): версия состояния (`stateVersion`), идемпотентность
  действий, фазы хода от сервера, «ход применён = приход состояния» (не локальная анимация).
- **Код комнаты:** ≥6 символов из криптослучайного non-ambiguous алфавита (≥~30 бит); жёсткий
  rate-limit/лок на неуспешные join (анти-перебор); код не работает на join после старта/заполнения.
- **Защита памяти (RAM — узкое место):** лимит активных комнат на сессию/IP; TTL + сборка мусора
  пустых/заброшенных комнат; cap общего числа комнат на процесс с graceful-отказом; лимит размера
  каждого сокет-сообщения; rate-limit на connect/create/join/dispatch.
- **Выбывший на своём ходу → игра обязана завершаться.** Если активный игрок выбыл, «пропуск хода»
  определяем явно (автозапись 0 в свободную категорию ИЛИ удаление места с пересчётом победителя),
  иначе `allCardsFull` никогда не станет true и `game:over` не наступит — вечный матч.
- **Создание партии — `createInitialState` на сервере**, action `NEW_GAME` от клиента сервер
  игнорирует/denied (иначе клиент задаёт свой seed/состав).

## Альтернативы

- **Клиент считает, сервер сверяет:** дублирование логики и риск рассинхрона — отклонено
  (у нас и так одно ядро на обе стороны).
- **Состояние комнат сразу в БД:** лишняя нагрузка и латентность в горячем пути; партия живёт
  в памяти, в БД идёт только ИТОГ — отклонено хранить ход игры в БД.

## Последствия

- ➕ Честность: единственный источник правды — сервер; при урезанном публичном состоянии
  (без `seed`/`rng`) клиент не может ни подделать, ни предсказать броски.
- ➕ Основной объём изменений локализован: новый сервер + `NetworkTransport` + аккуратные
  ДОБАВЛЕНИЯ в `core` (id/публичные функции/публичное состояние) + состояния соединения в UI.
  Логика/счёт ядра, `render3d`, `sound` — не переписываются.
- ➕ Комнаты независимы → горизонтальное масштабирование позже без переписывания (ADR-0007).
- ➖ Тайминг UI меняется с синхронного на асинхронный (ожидание сервера) — честно учесть в 2.1.
- ➖ Состояние комнаты живёт в памяти процесса: падение/**рестарт сервера (в т.ч. при каждом
  деплое!) = активные партии теряются** (для дружеских партий приемлемо; нужна нота пользователю
  - версия протокола; устойчивость к рестартам — возможное улучшение позже).
- ➖ Нужен аккуратный код синхронизации действий и порядка ходов на сервере.
