# ADR 0008 — Авторизация: вход через Google (OAuth) + гостевой вход

- Статус: accepted
- Дата: 2026-06-18

## Контекст

Вехе 2 нужны кабинеты (профиль, статистика, лидерборд) → нужен вход. Заказчик НЕ хочет
хранить пароли. При этом игра должна оставаться «сел и играешь» — высокий порог регистрации
убьёт желание позвать друзей быстро.

На старте Вехи 2 — только Google + гость. Но заказчик хочет, чтобы позже можно было ДОБАВИТЬ
email-регистрацию (и, возможно, другие соцсети) как ещё один способ входа — **без переписывания**
системы авторизации.

## Решение

Две двери на вход:

- **Зарегистрированный игрок — вход через Google (OAuth 2.0).** Пароли мы не храним и не
  видим — за них отвечает Google. У игрока появляется постоянная личность: профиль (имя,
  аватар), статистика, история партий, место в лидерборде.
- **Гость — без регистрации.** Заходит по коду/ссылке комнаты, вводит имя (или получает
  временное) и сразу играет. Гостю статистика/рейтинг НЕ копятся (нет постоянной личности).
  Захотел профиль/лидерборд → входит через Google и становится зарегистрированным.

Сессии — через подписанный токен (секрет в переменных окружения Railway). Любое входящее
действие на сервере проверяется (кто, в своей ли комнате, его ли ход).

**Несколько способов входа за единым контрактом «способ входа» (`AuthProvider`).** Система
авторизации не знает про конкретный провайдер — она работает через общий интерфейс, каждый
способ входа реализует его. На старте реализованы Google и гость; email и другие соцсети —
добавляются как новые реализации того же контракта, без переписывания платформы.

```ts
interface AuthProvider {
  id: 'google' | 'guest' | 'email' | string; // ключ способа входа
  authenticate(credentials): Promise<AuthIdentity>; // вернуть/создать личность
}
// AuthIdentity → один пользователь в БД может иметь несколько привязанных способов входа
// (например, позже привязать email к существующему Google-аккаунту), без миграции.
```

Модель пользователя в БД отделена от способа входа: «пользователь» (профиль, статистика) ↔
несколько «привязок способа входа» (provider + внешний id). Это позволяет добавить email или
соцсеть позже и даже привязать их к уже существующему Google-аккаунту — без миграции данных.

Задел на email-провайдер (когда дойдём): пароль хранится только как необратимый хеш
(argon2/bcrypt), плюс письма-подтверждения и сброс пароля — отдельная фича за тем же
контрактом `AuthProvider`. Гость — особый «способ входа» без постоянной личности (статистика
не копится).

### Приватность, публичность лидерборда, удаление аккаунта

- **Серверная валидация имени.** Имя (и гостя, и в профиле) видят ДРУГИЕ игроки → проверяем
  на сервере (длина, управляющие символы), а не только на клиенте. Клиентская проверка Вехи 1
  по сети не значит ничего (CLAUDE.md: экранировать пользовательский ввод).
- **Что публично в лидерборде:** только **отображаемое имя + аватар** игрока. Email/Google-id —
  никогда не публичны (только внутренний ключ привязки входа).
- **Удаление аккаунта закладываем сразу:** игрок может удалить аккаунт → удаляем профиль и
  привязки входа; в истории прошлых партий его участие анонимизируется (а не каскадно стирает
  чужие партии). Минимизируем хранимое: не держим лишних персональных данных.
- **Смена личности — только между партиями.** Гость становится зарегистрированным (вход Google)
  НЕ посреди активной партии: иначе ломаются сессия-место, реконнект-токен и зачёт статистики.
  Текущую гостевую партию доигрывает как гость; вход/привязка — в лобби/кабинете между играми.

### Безопасность входа и данных (правки по аудиту)

- **OAuth по правилам:** параметр `state` (анти-CSRF, привязан к сессии); `redirect_uri` —
  статический allowlist per-окружение (НЕ open redirect); «куда вернуть после входа» (deep-link в
  комнату) хранить server-side по ключу `state`, а не в URL; Google id-token проверять через
  `google-auth-library` (`aud`/`iss`).
- **Сессии (`jose` JWT):** короткий TTL access-токена + защищённый refresh; фиксированный алгоритм
  с явной проверкой (запрет `alg:none`); отзыв через `tokenVersion`/blocklist (логаут, удаление
  аккаунта); в WebSocket токен передавать в auth-payload рукопожатия, НЕ в query-string (попадает
  в логи).
- **Уникальность привязки:** пара `(provider, externalId)` — максимум к одному пользователю
  (unique-ограничение); привязка нового способа входа требует свежей аутентификации. Гостевая
  статистика не переносится задним числом.
- **Имена — серверная нормализация и фильтр** (имя видят ДРУГИЕ игроки, в т.ч. будущий чат Вехи 3):
  NFC-нормализация; запрет управляющих/zero-width/bidi-override (U+202E) символов и гомоглиф-бомб;
  лимит длины в кодпойнтах; дедуп/различение одинаковых имён в комнате; нигде не выводить имя в
  HTML/`title`/`innerHTML` без экранирования. Валидация общим контрактом `zod` на клиенте и сервере.
- **Логи без PII/секретов:** allowlist полей; токены/id-token/email/полные тела запросов с
  креденшелами НИКОГДА не логируются (логи Railway персистятся).
- **Лидерборд — только честные партии:** в рейтинг идут ТОЛЬКО естественно завершённые партии (все
  13 категорий, `isGameOver` на сервере по фактическому состоянию — не по клиентской команде
  «завершить») с участием ≥2 РАЗНЫХ зарегистрированных игроков. Гостевые и брошенные/кикнутые/
  forfeited партии в рейтинг НЕ идут. Защита от сговора двух аккаунтов — отдельная задача позже
  (честная оговорка, backlog).
- **Удаление аккаунта:** заменяем `user_id` в прошлых партиях на tombstone без обратной связи,
  вычищаем имя/аватар из кэша лидерборда, отзываем живые сессии (`tokenVersion`).

## Альтернативы

- **Email + пароль сразу**: универсальнее (не нужен Google), но мы храним хеши паролей и
  пишем письма-подтверждения и сброс пароля — больше кода и ответственности. Отложено как
  возможное расширение, не на старте.
- **Только гости (без аккаунтов)**: просто, но тогда невозможны статистика и честный
  лидерборд — отклонено, это цель Вехи 2.

## Последствия

- ➕ Ноль хранимых паролей → минимум ответственности и кода по безопасности входа.
- ➕ Гость = низкий порог: позвал по ссылке — играют сразу.
- ➕ Чёткая граница: личность (Google) нужна только для статистики/рейтинга.
- ➕ **Дверь под email/соцсети открыта:** контракт `AuthProvider` + «пользователь ↔ несколько
  привязок входа» позволяют добавить новый способ входа потом без переписывания и без миграции.
- ➖ Зависимость от Google как провайдера; игроку без Google-аккаунта на старте доступен
  только гостевой режим (до появления второго провайдера).
- ➖ Ручная настройка OAuth-приложения в Google Cloud — действие заказчика (его аккаунт).
