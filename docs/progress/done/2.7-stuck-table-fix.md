# 2.7-stuck-table-fix (фича в roadmap: Веха 2 → пост-деплойный багфикс)

Последний коммит по фиче: eac42d9. **ФИЧА ЗАКРЫТА.** НЕ на проде — выкатить `railway up`.
Файлы под-шага (тронем): server/platform/realtime.ts (SWEEP_EVERY_MS + ветка sweeper), server/platform/seating.ts
(+ чистый helper `abandonedGameAction`), server/platform/seating.test.ts. НЕ трогаем: shared/** (протокол
остаётся v5), клиент src/**, ядро, rooms.ts.

> Баг с живого теста (2026-06-22): на дежурном/открытом столе 1-на-1 один игрок вышел, второй доигрывал сам
> (форфейт за ушедшего срабатывал медленно — до ~120с ожидания на его ходу), затем второй тоже вышел — и стол
> ~2–3 минуты висел в списке как «in-game, 2 игрока», пока sweeper по grace его не сбросил. Прод сам очистился
> (in-memory), но окно «мёртвого» стола слишком длинное и выглядит как поломка.
>
> ПРИЧИНА: (1) период sweeper = 60с (== FORFEIT_MS) → форфейт добивается рывками раз в минуту, реальное
> авто-добивание хода ушедшего 60–120с; (2) брошенную ВСЕМИ партию sweeper сбрасывает только по
> GAME_GRACE_MS (120с) ДАЖЕ когда она уже доиграна форфейтом — а реконнектиться к завершённой партии не к чему.

## Под-шаги (один)

- [x] **1. Резвее sweeper + мгновенная уборка доигранной брошенной партии.** (eac42d9)
      • realtime.ts: `SWEEP_EVERY_MS` 60_000 → 15_000 — форфейт/уборка проверяются чаще. FORFEIT_MS (60с,
      ожидание реконнекта на ходу) и GAME_GRACE_MS (120с, grace брошенной ПАРТИИ) — политика, НЕ трогаем:
      они абсолютны по времени (`now - stamp > T`), период sweeper от них независим, поведение таймеров не меняется.
      • seating.ts: чистый `abandonedGameAction(room, now, graceMs, gameOver): 'reset' | 'delete' | null` —
      noLive && (gameOver || (emptiedAt!==null && now-emptiedAt>graceMs)) → 'reset' (persistent) / 'delete' (open);
      иначе null. Это и есть «партия доиграна (форфейт/естественно) + никого живого → убрать СРАЗУ, не ждать grace».
      • realtime.ts sweeper (in-game ветка): заменить текущее условие сноса на вызов `abandonedGameAction(room,
now, GAME_GRACE_MS, module.isGameOver(room.game.state))` → reset/delete. (runForfeits перед этим уже
      отработал в том же тике; если оба протухли — партия станет over прямо здесь, и уборка пройдёт сразу.)
      Тронем: realtime.ts (константа + ветка sweeper), seating.ts (helper), seating.test.ts (тест). НЕ трогаем
      протокол/клиент/ядро/rooms.
      Как проверим:
  - typecheck:server + eslint + test (юнит на `abandonedGameAction`: noLive+over→reset/delete по visibility;
    есть живой→null; not-over+grace-истёк→reset; not-over+до grace→null; пустой стол→reset/delete).
  - ЖИВОЙ локальный репро: поднять сервер с ВРЕМЕННО укороченными FORFEIT_MS/GAME_GRACE_MS/SWEEP (env или
    правка-непуш), 2 socket-клиента на дежурный стол → старт → оба выходят → `/tables` показывает возврат в

## Открытый вопрос (реши на гейте)

- **FORFEIT_MS = 60с** (сколько ждём реконнекта ушедшего на ЕГО ходу) — предлагаю ОСТАВИТЬ: баланс «не
  форфейтить из-за короткого блипа сети». Можно укоротить до ~30с, если хочется ещё резвее (минус — менее
  терпимо к обрыву мобильного интернета). По умолчанию не трогаю.

## Хвосты

- «Waiting for…» countdown vs реальный форфейт — после этого фикса расхождение сильно меньше (форфейт ~60–75с,
  countdown 60с). Полное выравнивание (показывать запас) — остаётся в backlog миноров.

## Само-аудит плана (прокрутка, 2026-06-22) — план подтверждён, существенных правок нет

Перепроверил по углам:

- **НЕ намертво.** Даже если форфейт не добьёт партию (denied/duplicate), grace-ветка (`emptiedAt>grace`) всё
  равно уберёт стол — backstop сохранён в `abandonedGameAction`. Прод сам очистился → «медленно, не намертво».
- **Сброс безопасен.** `abandonedGameAction` срабатывает ТОЛЬКО при noLive → стол с живым игроком (экран
  победителя / «Play again») НЕ трогаем; Play again остаётся за игроком.
- **Диспозиции как в текущем коде:** persistent→reset, open/private→delete (поведение не меняется).
- **gameOver-immediate безопасен:** к завершённой партии реконнектиться не к чему, итог уже записан/показан до
  выхода. Ниша «переподключиться поглядеть итог после ухода ВСЕХ» — приемлемая потеря (редко, игра окончена).
- **Частота sweeper не ломает таймеры:** FORFEIT_MS/GRACE/READY_TIMEOUT абсолютны по времени (`now-stamp>T`),
  период проверок на них не влияет — лишь делает реакцию точнее. Лишняя работа раз в 15с — копеечная.
- **Пол ~60с** уборки = FORFEIT_MS (ждём реконнекта последнего ушедшего на ЕГО ходу). Быстрее — только укоротив его.

Итог по таймингу: дохлый стол очистится за **~60–75с** (вместо ~2–3 мин) в сценарии заказчика.

ДВЕ опциональные «крутилки» (по умолчанию НЕ трогаю — это политика реконнекта):

- `FORFEIT_MS` 60→30с: автопилот и финиш резвее; минус — менее терпимо к блипу мобильной сети.
- `GAME_GRACE_MS` 120→45с: быстрее убирает брошенную НЕдоигранную партию; минус — короче окно общего реконнекта.

Уточнение по живой проверке: юнит на `abandonedGameAction` покрывает РЕШЕНИЕ; sweeper-интеграция — socket-слой
(известный непокрытый хвост). Реальный прогон: локальный socket-репро с укороченными таймерами ЛИБО контрольный
ретест на ПРОДЕ после деплоя (2 вкладки → оба выходят → стол в `waiting` за <1 мин). Выберу по факту прогона.
