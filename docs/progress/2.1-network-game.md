## План под-шага 2.1.d-1 — Подключение онлайна (сантехника + экран соединения)

**Цель.** Дать приложению режим «online»: по нажатию «Play online» клиент создаёт реальный сокет +
`NetworkTransport`, подменяет им активный транспорт в существующем `gameStore` (локальная партия и её
автосейв НЕ трогаются), показывает экран соединения со статусами, и когда от сервера приходит сетевое
состояние — роутер показывает `GameScreen`. Гейтинг кнопок/баннеры «ход соперника» — это 2.1.d-2.

**Решения по границам (важно — обсудить ДО кода):**

1. **Подмена транспорта в ОДНОМ сторе (как согласовано).** `createGameStore` сейчас замыкает методы
   (`roll`/`score`/…) на единственный `transport`. Рефактор: храним изменяемую ссылку `active` и
   маршрутизируем `dispatch`/`getState`/`reset` через неё; добавляем `goOnline()`/`goLocal()`, которые
   отписывают старый транспорт и подписывают новый, зеркаля его состояние в стор. `LocalTransport`
   (singleton + автосейв в localStorage) остаётся ЖИВ; online создаёт СВЕЖИЙ `NetworkTransport` на
   сессию и `reset()`-ит его (отключает сокет) при выходе. Развод localStorage соблюдён:
   `NetworkTransport` к `GameStorage` не прикасается (правило 2.1.c).

2. **Где живёт статус соединения/комнаты.** `src/platform/net.ts` становится владельцем «онлайн-сессии»:
   создаёт сокет (`io` с `auth.protocolVersion`), вешает обработчики СОКЕТА (connect/connect_error/
   disconnect/`protocol:mismatch`) И КОМНАТЫ (`MSG.joined`/`MSG.full`/`MSG.notFound`), агрегирует их в
   единый `OnlineStatus` и отдаёт через колбэк; конструирует `NetworkTransport(socket)`. Это НЕ требует
   правок `NetworkTransport.ts` (socket.io допускает несколько слушателей на событие — транспорт слушает
   `state`/`joined` для своих нужд, net.ts параллельно — для статуса). Модель статуса:
   `connecting | offline | mismatch | waiting | full | playing` (где `connecting`→`waiting` после
   `joined`; `playing` — когда пришло первое состояние; `full`/`mismatch`/`offline` — терминальные для
   экрана). `room:not-found` в 2.1 недостижим (комната `dev` авто-создаётся) — обрабатываем как `offline`-
   подобный, полноценно — 2.2.d.

3. **`pending` и `myPlayerId` — НЕ в d-1, а в d-2.** Скелет упоминал проброс «status + playerId +
   pending». Предлагаю оставить в d-1 только **статус соединения/комнаты**, а проброс `pending`
   (блокировка кнопок) и `myPlayerId` (чей ход) — в d-2, где они РЕАЛЬНО используются для гейтинга. Так
   d-1 не трогает `NetworkTransport.ts`, остаётся сфокусированным, а критерий d-1 (партия стартует между
   двумя вкладками, чужой ход сервер отклоняет) достигается и без клиентского гейта — отказ ловит сервер
   (`denied`, звук уже играет с 2.1.c). ← главное решение под-шага, прошу подтвердить.

**Что делаем (файлы — ТРОНЕМ):**

- EDIT `src/platform/net.ts` — добавить `OnlineStatus` и `createOnlineSession(onStatus): { transport,
dispose }`: создаёт сокет, агрегирует статус сокета+комнаты, конструирует `NetworkTransport`; `dispose`
  = `transport.reset()` (отключает сокет). Старые `connectPlatform`/`ConnStatus` удалить (их единственный
  потребитель `OnlineComingSoon` уходит).
- EDIT `src/state/gameStore.ts` — `active`-ссылка + маршрутизация методов через неё; поля
  `mode: 'local' | 'online'` и `onlineStatus: OnlineStatus | null`; методы `goOnline()` (свап на сетевой
  транспорт + подписка на статус) и `goLocal()` (dispose сетевого, возврат на сохранённый локальный,
  `onlineStatus=null`). Зеркалирование `(state, events)` переносим на активный транспорт при свапе.
- NEW `src/ui/screens/OnlineScreen.tsx` — экран соединения (заменяет `OnlineComingSoon` в роутере): на
  mount `goOnline()`, на размонтирование/«← Back to menu» — `goLocal()` + `setView('menu')`; показывает

  секционному требованию Вехи 2.
- DELETE `src/ui/screens/OnlineComingSoon.tsx` — заменён `OnlineScreen` (его проба соединения поглощена).
- EDIT `src/App.tsx` — заменить импорт/рендер `OnlineComingSoon` на `OnlineScreen` (ветка `view==='online'`
  при отсутствии состояния; когда придёт сетевое `state` — уже существующая ветка `state ? GameScreen`).
- EDIT `src/ui/theme.css` — переиспользовать `.coming`/`.conn-status`; добавить классы статусов `waiting`/
  `full` (минимальная дельта).
- EDIT `docs/progress/2.1-network-game.md` — отметки.

**Файлы — НЕ трогаем:** `NetworkTransport.ts` (контракт/логика 2.1.c достаточны; `pending`/`playerId`
проброс — d-2), `Transport.ts`/`LocalTransport.ts` (контракт неизменен), `shared/protocol.ts`, `server/*`,
ядро, `GameScreen`/таблица/кости (гейтинг — d-2). Новых зависимостей нет (`socket.io-client` уже стоит).

**Граничные случаи:**

- Сервер не запущен → `connect_error` → статус `offline`, экран это показывает, «← Back to menu» работает.
- Версия протокола не совпала → `protocol:mismatch` → `mismatch` («refresh»), сокет закрыт, без ретраев.
- Вошёл первым, соперника нет → `joined` без состояния → `waiting` («Waiting for an opponent…»).
- Комната занята (2/2) → `room:full` → `full`, остаёмся на экране, выход в меню доступен.
- Выход из онлайна до старта партии → `goLocal()` dispose-ит сетевой транспорт (disconnect), локальная
  партия/автосейв целы (их вообще не трогали).
- Свап туда-обратно (online→local→online) → каждый раз свежий сокет/транспорт; нет утечки подписок
  (старый `unsub()` вызывается при свапе).

## СЛЕДУЮЩЕЕ: 2.1.d — структура и подход (СОГЛАСОВАНО с заказчиком, до кода)

2.1.d оказался крупным (стор + `net.ts` + новый экран соединения + роутер `App.tsx` + гейтинг
`GameScreen`), поэтому РАЗБИТ на два под-шага (выше): **2.1.d-1** и **2.1.d-2**. Детальный PLAN
под 2.1.d-1 (файлы/граничные случаи/как проверим) пишется В НАЧАЛЕ следующей сессии — здесь только
согласованный каркас, чтобы пережить `/clear`.

**Согласованный подход — переключение транспорта в ОДНОМ сторе (рекомендация принята):**
В режиме «online» подменяем активный транспорт в существующем `gameStore`: отписались от
`LocalTransport` → создали и подписались на `NetworkTransport`; возврат в меню — обратно на локальный.
Весь UI (экраны/таблица/кости) НЕ переписываем — он не знает, локальная игра или сетевая (ADR-0003).
Отвергнут вариант «отдельный стор на режим» (тронул бы весь UI).

**2.1.d-1 — Подключение онлайна (сантехника + экран соединения):**

- `src/platform/net.ts` — фабрика: создать сокет + `NetworkTransport`, отдать статус соединения.
- `src/state/gameStore.ts` — уметь подменять активный транспорт (online↔local), пробросить в стор
  статус соединения + `playerId` + `pending` (концертные методы `NetworkTransport`, не ломая контракт
  `Transport`).
- Новый экран соединения (вместо `OnlineComingSoon` для online-потока): состояния connecting/
  connected/offline/mismatch/«ждём соперника»/«комната занята»; «← В меню» = покинуть комнату.
- `App.tsx` — когда пришло сетевое состояние, роутер показывает `GameScreen` (как сейчас).
- Критерий: две вкладки соединяются, партия стартует, ходы идут (чужой ход сервер отклоняет).

**2.1.d-2 — Гейтинг `GameScreen` под сеть:**

- Контролы блокируются по «не мой ход» (`players[current].id !== myPlayerId`) + `pending` +
  «нет соединения» (а НЕ по локальному `settling`, ADR-0013); баннеры «Ход соперника» /
  «Соединение потеряно»; корректный выход из сетевой партии.

**НЕ в 2.1.d (это 2.1.e):** проигрывание чужого броска (тумбл костей соперника к значениям сервера),
обработка разрыва/реконнект. Кросс-секционное требование Вехи 2 (англ. строки, a11y, состояния
загрузка/пусто/ошибка, мобильный адаптив) — применять к новым экранам сразу.

## План под-шага 2.1.c — Оживить `NetworkTransport` под интерфейс `Transport`

**Цель.** Заменить заглушку `NetworkTransport` реальной реализацией интерфейса `Transport` (ADR-0003):
говорит с авторитетным сервером 2.1.b по Socket.IO, кэширует публичное состояние, гейтит действия
по `pending` и отбраковывает устаревшие версии (ADR-0013). Ядро/`LocalTransport`/UI-экраны НЕ трогаем.
Подключение транспорта в приложение (переключение режима, экраны соединения, блокировка кнопок) —
это 2.1.d; здесь только сам класс + тесты + живой прогон против сервера.

**Решения по границам (важно — обсудить ДО кода):**

1. **`getState()` синхронный, сервер шлёт `PublicGameState` (без `seed`/`rng`).** Транспорт кэширует
   последнее публичное состояние и возвращает его синхронно. Контракт возвращает `GameState`;
   публичное состояние — это `Omit<GameState,'seed'|'rng'>`, UI эти поля не читает. Отдаём кэш через
   узкий, документированный каст на границе `getState` (`as GameState`) — БЕЗ правки контракта
   `Transport`/`LocalTransport`/стора (иначе тронем пол-проекта ради двух неиспользуемых полей).
2. **`pending`-гейт внутри транспорта (ADR-0013).** `dispatch` поднимает `pending` и шлёт действие с
   `actionId`; пока `pending` — новые `dispatch` игнорируются (анти-двойной Roll/Score). Снимается при
   приходе более новой версии состояния ИЛИ `denied` на наш `actionId`. Индикация `pending` для UI
   (блокировка кнопок) — 2.1.d; здесь гейт живёт в транспорте.
3. **Версия-гейт.** Кэш применяется, только если `stateVersion > текущей`; иначе игнор (лечит
   переупорядочивание/дубли/хвост после реконнекта, ADR-0013).
4. **Сокет инъецируется (тестируемость).** Конструктор принимает уже подключённый сокет (узкий
   интерфейс `on/emit/disconnect` — его удовлетворяет `Socket` из `socket.io-client`). Фабрику
   реального сокета (через `socket.io-client`) и связку со стором по режиму делаем в 2.1.d вместе с
   экранами соединения. Тест подаёт фейковый сокет и гоняет события без сервера.
5. **`NEW_GAME` и `reset`.** Партию создаёт сервер (авто-старт), поэтому `dispatch(NEW_GAME)` транспорт
   игнорирует. `reset()` — отключиться от сокета, обнулить кэш, уведомить `(null, [])`. Вход в комнату
   (`room:join 'dev'`) — на конструкции (минимум 2.1; коды/лобби — 2.2).
6. **`denied` → переиспользуем существующий звук/обработку.** На `denied` нашего `actionId` снимаем
   `pending` и эмитим подписчикам синтетическое доменное событие `{type:'action:denied', reason}` с
   текущим кэшем — Веха 1 уже играет на него «отказ», новый код в звуке не нужен.

**Что делаем:**

- EDIT `src/transport/NetworkTransport.ts` — реальная реализация: подписка на `MSG.state`/`MSG.denied`/
  `MSG.joined`/`MSG.full`; кэш `PublicGameState` + `stateVersion`; маппинг `Action`→`NetworkAction`
  (drop `NEW_GAME`, у `ROLL` нет `values`); `actionId` (по умолчанию `crypto.randomUUID`, инъекция в
  тест); `subscribe`/`getState`/`reset`; узкий интерфейс сокета.
- NEW `src/transport/NetworkTransport.test.ts` — фейковый сокет: применяет более новую версию и
  уведомляет; игнорит устаревшую/равную версию; `pending` гейтит второй `dispatch`; `denied` снимает
  `pending` и эмитит `action:denied`; `dispatch(NEW_GAME)` игнор; `ROLL` уходит без `values`; `reset`
  отключает и обнуляет.

**Файлы — ТРОНЕМ:** `src/transport/NetworkTransport.ts`, `src/transport/NetworkTransport.test.ts`,
`docs/progress/2.1-network-game.md`.

**Файлы — НЕ трогаем:** `Transport.ts`/`LocalTransport.ts` (контракт неизменен), `src/state/*`
(переключение режима — 2.1.d), `src/platform/net.ts` (фабрика сокета — 2.1.d), `shared/protocol.ts`,
`server/*`, UI-экраны, ядро. Новых зависимостей нет (`socket.io-client` уже стоит).

**Граничные случаи:**

- Пришла версия ≤ кэшу → игнор (stale), `pending` НЕ трогаем без необходимости.
- `dispatch` пока `pending` → игнор (двойной клик/лаг).
- `denied` на наш `actionId` → снять `pending`, эмитнуть `action:denied`; на чужой/неизвестный — игнор.
- `dispatch` до входа в комнату/до старта партии → действие уйдёт, сервер ответит `denied no-game`
  (наш `pending` снимется по denied). Допустимо для 2.1.
- `getState()` до первого состояния → `null`.

**Как проверим (живьём, с артефактами):**

1. `npm run test` — НОВЫЙ `NetworkTransport.test.ts` (версия-гейт, pending, denied, маппинг, reset) +
   все прежние зелёные.
2. `npm run lint`, `npm run build` (клиент, tsc) — чисто, типы ок.
3. **Живой прогон (tsx):** поднять сервер; скрипт создаёт ДВА реальных `NetworkTransport` (два игрока,
   реальные сокеты `socket.io-client`) → авто-старт → текущий игрок `dispatch(ROLL)`/`SCORE`; показать
   `getState()` и события подписчиков с растущей версией, срабатывание `pending`-гейта и `denied` на
   действие не в свой ход. Это доказывает работу реального класса против сервера 2.1.b.

**Аудит CHECK (code-reviewer) и фиксы (попытка 1/3):**

- 🟠 MAJOR-1 — `reset` не отписывался от сокета: поздний `state`-пакет мог «воскресить» партию после

- 🟡 MINOR-3 — `onDenied` эмитил `action:denied` даже без in-flight действия (дубль → двойной «отказ»).
  Фикс: реагируем только если denied относится к нашему `pendingActionId`. Тесты на оба добавлены.

Хвосты / спящие баги (тех-долг 2.1.c, не блокеры — в roadmap-backlog при закрытии фичи 2.1):

- MINOR-2: `onState` снимает `pending` по приходу ЛЮБОЙ новой версии, не по `actionId` (StatePayload
  его не несёт). Для пошаговой игры безопасно; точный матч — когда сервер положит `appliedActionId`

- MINOR-4: входящий `state`/`denied` принимается слепым кастом без рантайм-валидации схемы (сервер
  свой/авторитетный — приемлемо). Рантайм-гард схемы (zod) — позже, вместе с валидацией 2.2.b.
- `room:full`/`room:not-found` не обрабатываются на клиенте — продуктовые состояния 2.2.d.

## План под-шага 2.1.b — Авторитетный сервер: CSPRNG + комнаты + версия/идемпотентность

**Цель.** Сервер становится авторитетным: принимает действия игроков, проверяет их, генерирует
значения костей криптостойко (ADR-0012), прогоняет ядро (`reduce`), нумерует состояния
(`stateVersion`, ADR-0013) и рассылает ПУБЛИЧНОЕ состояние (без `seed`/`rng`) + события всем в
комнате; `denied` — лично автору. Ядро НЕ трогаем (всё нужное добавлено в 2.1.a). Клиентский
транспорт/UI — это 2.1.c/d, НЕ здесь.

**Решения по границам (важно — обсудить ДО кода):**

1. **Минимальная комната для 2.1 (не полноценные коды/лобби — это 2.2).** Чтобы выполнить
   критерий 2.1.e «партия между двумя вкладками», сервер заводит МИНИМАЛЬНЫЙ вход: клиент шлёт
   `room:join { roomId }` (для 2.1 — общий литерал, напр. `"dev"`), сервер сажает на свободное
   место, авто-стартует партию при 2 игроках. Генерация кодов из CSPRNG, валидация, хозяин,
   кик, лобби-UX — всё это **2.2**, поверх этой же модели комнаты. Здесь — каркас комнаты + цикл.
2. **`playerId` без аккаунтов.** Аккаунты — 2.3. Здесь сервер выдаёт стабильный id места при
   join (напр. `seat-<rnd>`), маппит `socketId → playerId`. `createInitialState(playerIds)`
   получает их от платформы (ADR-0011). Полный reconnect-токен на место — 2.4; здесь при разрыве
   просто освобождаем место (минимум, расширяется в 2.1.e/2.4).
3. **Версия протокола → 2.** Добавляем реальные игровые сообщения; старый «hello-world» обмен
   2.0.c несовместим. Обе стороны берут константу из `shared/protocol.ts` (клиент `net.ts` уже
   так делает) — бамп безопасен.
4. **Идемпотентность по `actionId`.** Действие клиента несёт `actionId`; сервер обрабатывает
   действия комнаты строго последовательно и игнорирует повтор (ADR-0013). `forVersion` не вводим
   — для пошаговой игры `actionId` + серийная обработка достаточно (анти-оверинжиниринг).

**Что делаем:**

- **CSPRNG значений костей** (`server/platform/rng.ts`, NEW): `rollDiceValues(count): DieValue[]`
  через `node:crypto` (`randomInt`). Источник инъекции — параметром, чтобы тест был детерминирован.
- **Контракт `GameModule`** (`server/platform/gameModule.ts`, NEW): TS-интерфейс из ADR-0011
  (`createInitialState`/`reduce`/`isPlayersTurn`/`isGameOver`/`getResult`/`toPublicState`).
- **Yahtzee как `GameModule`** (`server/games/yahtzee/index.ts`, EDIT): тонкий адаптер над `core`
  (createInitialState→`createGame`; остальное — реэкспорт функций 2.1.a). `id` сохраняем.
- **Модель комнаты + авторитетный цикл** (`server/platform/rooms.ts`, NEW): реестр комнат в памяти
  (`Map`), посадка/освобождение мест, и ЧИСТАЯ `applyAction(room, action, actorId, rollValues)`:
  авторизация хода (`isPlayersTurn`), `NEW_GAME` от клиента → denied, для `ROLL` подставляем
  значения CSPRNG, `reduce`, `++stateVersion`, дедуп по `actionId`. Чистая логика отделена от
  сокетов → тестируема.
- **Сетевое подключение цикла** (`server/platform/realtime.ts`, EDIT): обработчики `room:join` и
  `action`; авто-старт при 2 игроках (серверный `NEW_GAME`); рассылка `state` (publicState +
  stateVersion + events) в комнату; `denied` — unicast автору; на `disconnect` освобождаем место.
- **Тесты** (`server/platform/rooms.test.ts`, NEW): идемпотентность (повтор `actionId` — без
  изменений), монотонность `stateVersion`, авторизация хода (чужой → denied), `NEW_GAME` от
  клиента → denied, `ROLL` подставляет 5 значений 1..6 и уважает held, конец игры → `getResult`.

**Файлы — ТРОНЕМ:**

- NEW `server/platform/rng.ts`
- NEW `server/platform/gameModule.ts`
- NEW `server/platform/rooms.ts`
- NEW `server/platform/rooms.test.ts`
- EDIT `server/games/yahtzee/index.ts` — тонкий `GameModule`-адаптер.
- EDIT `server/platform/realtime.ts` — обработчики join/action, рассылка.
- EDIT `shared/protocol.ts` — `PROTOCOL_VERSION=2`; wire-типы (NetworkAction + actionId; сообщения
  сервер→клиент: state-снимок, denied, room:joined/started/over, room-not-found). Без DOM/Node.
- EDIT `docs/progress/2.1-network-game.md` — отметки.

**Файлы — НЕ трогаем:** `src/core/*` (нужное добавлено в 2.1.a), клиентские `src/*`,
`src/transport/*`, `src/platform/net.ts` (это 2.1.c/d). Новых npm-зависимостей нет (`socket.io`,
`node:crypto` уже есть).

**Размер/риск дробления.** Оценка ~350–400 строк / 7 файлов — на ВЕРХНЕЙ границе правила (~300).
Кусок цельный («авторитетный сервер»). Держу как ОДИН коммит 2.1.b, но если при кодинге разойдётся
за ~300 — СТОП и разбиваю: 2.1.b-1 (protocol + GameModule + rng + rooms-чистая-логика + тесты),

**Граничные случаи:**

- `ROLL` с `values` ОТ КЛИЕНТА (попытка подсунуть кости) — wire-тип клиента без `values`; сервер
  игнорирует любые `values` из сети и ставит свои CSPRNG.

- 3-й+ сокет в полную комнату (2/2 для 2.1) → `room:full` (продуктовые состояния — позже 2.2.d).
- Разрыв во время партии → место освобождается (минимум; пауза/арбитраж — 2.1.e/2.4).

## План под-шага 2.1.a — Дополнить `core` для сети (чистые аддитивные функции)

**Цель.** Добавить в ядро то, что нужно серверу 2.1.b, НИЧЕГО не ломая (правила/счёт/тесты Вехи 1
без изменений; всё обратносовместимо). Только чистые функции/типы. Сервер/транспорт/UI — не здесь.

**Решение по границам (важно):**

- **События ядра остаются index-based** (`DomainEvent.player: number`). Маппинг в стабильный
  `playerId` для рассылки клиентам — серверный слой (2.1.b/c), НЕ ядро. Так не трогаем типы событий
  и их потребителей (звук/celebration/UI) — Веха 1 цела (совпадает с находкой аудита).
- `toPublicState` для Yahtzee **без `forPlayerId`**: у нас нет приватной для игрока информации
  (кости/карточки видны всем); секрет только `seed`/`rng`. Параметр не нужен (упрощаем контракт).

**Что добавляем (всё ADDITIVE):**

1. **Внешние id игроков.** `createGame(players: { name: string; id?: string }[], seed)` — если `id`
   задан (сервер привяжет к сессии/аккаунту), берём его; иначе прежний фолбэк `p${i}`. Локальный
   путь (`NEW_GAME` с `{name}[]`) не меняется.
2. **Инъекция значений броска (ADR-0012).** `ROLL` получает опциональное `values?: DieValue[]`
   (длина 5, по позиции). Если задано — небросаемые (held) кости сохраняются, остальные берут
   `values[i]` (сервер подаёт CSPRNG-значения); если НЕ задано — прежний путь через `rng` ядра
   (локальная игра). Валидация: длина 5 и каждое 1..6, иначе `denied('bad-roll-values')`.
3. **`isPlayersTurn(state, playerId): boolean`** — `phase==='playing' && players[current].id===playerId`.
4. **`isGameOver(state): boolean`** — `phase==='over'`.
5. **`getResult(state): GameResult`** — обобщённый итог для статистики/лидерборда:
   `{ winnerIds: string[]; standings: { id, name, total }[] }` (победители — по стабильному `id`).
6. **`toPublicState(state): PublicGameState`** — `Omit<GameState,'seed'|'rng'>` (снять секреты RNG).

  `GameResult`. (`Player.id` уже есть.)

  новые экспортируемые функции `isPlayersTurn`, `isGameOver`, `getResult`, `toPublicState`.

- EDIT `docs/progress/2.1-network-game.md` — отметки.

**Файлы — НЕ трогаем:** `rng.ts`/`scoring.ts` (используем), `DomainEvent` и его потребители
(звук/UI/celebration), `transport/*`, `server/*` (это 2.1.b), клиентские экраны. Никаких новых зависимостей.

**Граничные случаи:**

- `ROLL` с неверными `values` (не длина 5 / вне 1..6) → `denied('bad-roll-values')`, состояние не меняется.
- `ROLL` без `values` → прежний детерминированный путь через `rng` (локальная игра, тесты Вехи 1 целы).

- `toPublicState` оставляет `gameId` (публичный), убирает только `seed`/`rng`.
