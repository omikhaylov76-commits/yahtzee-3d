## Решения (зафиксированы 2026-06-20)

- **dev-БД = одна Railway-база** на старте (и dev, и prod; делегировано заказчиком). Разделим при росте.
- **PostgreSQL создан** на Railway (`Postgres ● Online`, проект yahtzee-3d). Подключение:
  - рантайм сервера на Railway → внутренний `DATABASE_URL` (приватная сеть, reference `${{Postgres.DATABASE_URL}}`);
  - локально (миграции/dev с моей машины) → `DATABASE_PUBLIC_URL` (TCP-прокси) в `.env`.
- **Крючки монетизации** в таблице users: `tier` + `entitlements` (пустые полочки, ADR no-pay-to-win) —
  чтобы потом не мигрировать БД под выбранную модель.
- **Политика зачёта в рейтинг (РЕШЕНО 2026-06-20, подтверждено заказчиком).** В сетевой рейтинг/лидерборд
  идут ТОЛЬКО естественно доигранные СЕТЕВЫЕ партии с ≥2 РАЗНЫМИ зарегистрированными игроками. Брошенные/
  прерванные — не в рейтинг НИКОМУ (ни ушедшему, ни оставшемуся: «техническая победа за уход» НЕ начисляется —
  анти-сговор). Вышедший из СЕРЕДИНЫ не пишется вовсе (партия не доигрывается → записи нет); кто успел отыграть
  все свои ходы и отключился под конец — пишется с РЕАЛЬНЫМИ очками. Локальные партии в рейтинге не участвуют
  (через сервер не проходят). Реализация: запись истории — 2.3.d; фильтры рейтинга — 2.4.a.
- **Игровой ник — отдельный и уникальный (РЕШЕНО 2026-06-20, ADR-0015).** НЕ редактируем Google-имя; ник —
  отдельное поле, глобально уникален без учёта регистра (ключ = `normalizeName`+casefold, UNIQUE в БД ловит
  гонку), обязателен для зарегистрированного (онбординг 1-го входа + гейт сетевой игры), правила мягкие
  (`shared/names`) + резерв системных имён, освобождается при удалении. В игре/истории/лидерборде — ник.
- **Вход — остаётся Google.** Email+пароль НЕ сейчас; заложен на будущее (ADR-0008 + backlog roadmap) как
  ещё один `AuthProvider` без переписывания/миграции (по запросу заказчика 2026-06-20 «чтобы не забыть»).
- **Удаление = физическое затирание PII** (профиль + снимки имени в истории → «Deleted player»), `user_id`
  СОХРАНЯЕМ (честность рейтинга), отвязка Google (`identities`), отзыв сессий. Пересматривает «join на
  deleted_at» из 2.3.d в пользу затирания (история впервые читается только сейчас — кабинетом).
- **Статистика** одним SQL-запросом; `zod` на тело смены ника; общий HTTP-гейт сессии (вынести из `/auth/me`).

## Хвосты / спящие баги

- **Прод подключён к БД** (2.3.b): в yahtzee-3d задан `DATABASE_URL` — ВНУТРЕННИЙ адрес Postgres прямым
  значением (через CLI, не reference). Вход end-to-end в проде записал аккаунт ✓. _При смене пароля
  Postgres обновить вручную (или перевести на reference `${{Postgres.DATABASE_URL}}` в Railway dashboard)._
- **Google app — режим Testing/Published:** owner (заказчик) входит и в Testing; для ДРУЗЕЙ нужно
  «Publish app» (любой Google) ИЛИ добавить их почты в Test users. Проверить перед тестом с людьми.
- **Ротация Client Secret:** Secret проходил через чат — после пилота сделать Reset secret в Google Cloud.
- **SSL для публичного подключения** не понадобился (Railway TCP-proxy принял без `sslmode`); если на
  другой машине drizzle-kit/pg потребует SSL — добавить `?sslmode=require` в `.env`.
- **Прод отстаёт по коду d (2.3.d):** запись итогов есть в коде/локальной БД, но на проде сервер ещё без
  d-кода — записи в проде начнутся ТОЛЬКО после редеплоя (`railway up`). Тогда же — контрольный e2e: реальный
  сетевой матч двух залогиненных → строка в `matches`. Миграция на общую БД уже применена (таблицы есть).
- **realtime-хук записи без интеграционного socket-теста** (как и весь realtime — известный хвост 2.1/2.2):
  логика вынесена в чистый `onGameOver` (покрыт юнитами), путь «реальный game:over → recordMatch» — живым
  прогоном. Регресс-тест socket-слоя — кандидат.
- **Идемпотентность записи — только в памяти** (single-process, ADR-0009): повтор `game:over` невозможен (фаза
  терминальна), дубль actionId отсечён до success-ветки. БД-якорь (UNIQUE id партии + `ON CONFLICT`) — аддитивно
  при переходе на мульти-реплику/Redis (принятый риск, сейчас не нужен).

## План под-шага 2.3.b — Вход через Google (делегировано: «как лучше/технически обоснованно»)

**Решения (зафиксированы 2026-06-20):**

- Authorization Code flow, `google-auth-library@^10`. Client ID получен; Secret — в env (заказчик).
- **state (CSRF):** server-side `Map<state, expiresAt>` + TTL 10 мин, сверка+удаление на callback. Без
  cookie/jose до 2.3.c (single-process — достаточно; рестарт во время входа = повтор, приемлемо).
- **redirect_uri:** из env `GOOGLE_REDIRECT_URI` (dev `http://localhost:3001/auth/google/callback`,
  prod `https://yahtzee-3d-production.up.railway.app/auth/google/callback`). Должен совпадать с Google client.
- **Аккаунт:** `findOrCreateUser` — identity по (provider, sub); нет → создать users+identities в транзакции.
- **Граница:** 2.3.b → «аккаунт в БД». Постоянная сессия (cookie/jose) — 2.3.c. Callback пока отдаёт
  временную страницу «вошёл как …».

**Разбивка:** b-1 (сервер: AuthProvider+google+routes+upsert+прод-линковка БД) → b-2 (клиент: кнопка входа).

## План под-шага 2.3.d — Запись итогов партий (Путь A: данные раньше витрины)

> **Версия 2 — после независимого аудита (2 ревьюера + самопроверка, 2026-06-20).** Изменения к v1
> отмечены [АУДИТ]. Сводка правок — в конце раздела.

**Цель.** Сервер записывает итог КАЖДОЙ естественно завершённой сетевой партии в БД, чтобы кабинет (e)
показал реальную статистику, а лидерборд (2.4) — построился. Источник истины — авторитетный сервер
(`module.getResult`, ADR-0009/0011). Ядро НЕ трогаем — `getResult`/`isGameOver` уже есть (2.1.a).

**Контракт итога — типизированный общий контракт шва [АУДИТ C3].**
Сейчас `GameModule.getResult(): Result` — безымянный дженерик, но платформенный stats-слой ОБЯЗАН знать
форму итога, чтобы его записать → дженерик «лжёт», а чтение `GameResult` из `src/core` в платформе = протечка
игры (она уже есть в `rooms.ts`, не углубляем молча). Решение: поднять форму итога в **платформенный
контракт** `MatchResult = { winnerIds: string[]; standings: { id; name; total }[] }` рядом с `GameModule`
(`server/platform/gameModule.ts`), типизировать `getResult(): MatchResult`. Ядро `src/core` продолжает
экспортировать свой `GameResult` (структурно идентичен) — адаптер `games/yahtzee/index.ts` декларирует
совместимость, компилятор проверит. Платформа читает `MatchResult` ЛЕГАЛЬНО (это контракт шва, не «форма
игры»). ADR-0011 дополнить абзацем «итог = типизированный общий контракт, не безымянный дженерик».
`id` в standings = стабильный `playerId` (= `seat.playerId`); победа = членство в `winnerIds` (ничья →
несколько). Триггер конца — событие `{type:'game:over'}` в `result.events` (ровно один раз: фаза `over`
терминальна).

**Модель данных (нормализуем ОДИН раз — хватит и на историю, и на лидерборд 2.4):**

- `matches`: `id` uuid PK, `game_id` text NN ('yahtzee' = `module.id`), `finished_at` timestamptz NN default
  now, `player_count` int NN (всего мест), **`registered_count` int NN** [АУДИТ C1] — число мест с аккаунтом.
  _Зачем registered_count:_ лидерборд 2.4 фильтрует «честные» партии `WHERE registered_count >= 2` одним
  индексируемым условием; из `player_count` (включает гостей) это невыразимо, а пересчёт задним числом по
  всей истории — больно. Индексы под 2.4 — позже (поле закладываем сейчас, оно аддитивно-дорогое).
- `match_players`: `id` uuid PK, `match_id` uuid NN FK→matches **ON DELETE CASCADE**, `user_id` uuid NULL
  FK→users **(ON DELETE по умолчанию = NO ACTION)** [АУДИТ C2] — `null` = СТРОГО гость (аккаунта не было).
  Tombstone-удаление НЕ трогает эти строки (юзер не удаляется физически), поэтому SET NULL вреден (тихо
  обнулил бы историю при случайном хард-делите) — NO ACTION фиксирует инвариант «аккаунт с историей физически
  не удаляется». `display_name` text NN (СНИМОК имени на момент партии), `total` int NN, `is_winner` bool NN
  default false. Индекс по `user_id` (запрос статистики игрока). **`seat`-колонку УБРАЛИ** [АУДИТ MINOR] —
  порядок мест никто не читает (YAGNI, ADR-0011 против крючков); понадобится для «карточки матча» — добавим в e.
- _Снимок `display_name` берём из `standings[].name`_ [АУДИТ MAJOR-1] — это имя места, ЗАСТЫВШЕЕ на старте
  партии (платформа кладёт `seat.name` в ядро при `startGame`), уже нормализованное `normalizeName`+`dedupeName`
  (XSS/невидимки/дедуп сняты на входе). Для ИСТОРИИ застывшее имя правильнее живого `seat.name` (сменит ник в
  кабинете — старая партия покажет имя на тот момент). `user_id` — из места по `playerId` (см. сборку строк).
- _Tombstone (в e):_ удаление = `users.deleted_at`+аноним.+`tokenVersion`++; в чужой истории удалённого
  показываем «Deleted player» живым джойном по `users.deleted_at` (`user_id` СОХРАНЯЕТСЯ). Здесь не строим.

**Правило записи (естественное завершение «выпадает» из точки триггера):**

- Пишем ТОЛЬКО когда действие игрока привело к `game:over` (forfeit/disconnect-снос фазы `over` не дают —
  значит брошенные/прерванные партии НЕ записываются автоматически, как и требует 2.3.e/2.4.a). _Следствие
  для e_ [АУДИТ MINOR-4]: «сыграно» в кабинете = доведённые до конца партии с моим участием, НЕ все.
- Пишем матч, ТОЛЬКО если есть ≥1 ЗАРЕГИСТРИРОВАННЫЙ участник. **Проверка — ПОСЛЕ сборки строк** [АУДИТ MAJOR-2]:
  `userId` нет в `standings`, он разрешается по местам → guard `players.some(p => p.userId != null)` (`!= null`
  ловит и `undefined`, и `null`) у ВЫЗЫВАЮЩЕГО, чистая `buildMatchRows` строки отдаёт всегда. `match_players`
  пишем по ВСЕМ местам (имена соперников-гостей нужны истории), `user_id` гостя = null.
- Запись ВНЕ горячего пути и не валит игру: fire-and-forget. **`.catch` логирует на уровне ERROR с контекстом**
  (кандидат-`matchId`/счётчики/текст ошибки) **БЕЗ имён/PII** [АУДИТ MAJOR-3 + требование 2.3.d «логи без PII»],
  чтобы потерю можно было заметить. _Принятый риск:_ однократная запись без ретрая — редкая потеря матча при
  сбое БД приемлема на пилоте (durable-очередь/outbox — за рамками). Вставка `matches`+`match_players` — в
  ОДНОЙ транзакции (нет «матча без игроков»).
- _Идемпотентность_ — терминальностью фазы (повторного `game:over` нет; дубль `actionId` отсечён `result.duplicate`
  ДО success-ветки; ре-снапшот шлёт `events:[]`). _Принятый риск_ [АУДИТ MAJOR-3]: защита только в памяти
  (single-process, ADR-0009) — БД-якоря (UNIQUE по id партии + `ON CONFLICT DO NOTHING`) НЕ ставим сейчас, при
  переходе на мульти-реплику/Redis добавим аддитивно (двойная запись требует 2 процессов с общим in-memory
  состоянием — на текущей архитектуре невозможна).
