# 2.2-online-rooms (фича в roadmap: Веха 2 → **2.2 Меню онлайна, комнаты и коды**)

Последний коммит по фиче: 824129d (2.2.a-2)
Файлы под-шага (тронем): см. «Под-шаг 2.2.a-1» ниже.

## О фиче (что строим в 2.2)

Сейчас (2.1) онлайн — ОДНА жёстко зашитая комната `'dev'`, capacity 2, авто-старт при двоих.
2.2 превращает это в нормальный путь: **создать комнату → получить код → друзья входят по коду →
лобби (список, кто хозяин) → хозяин жмёт Start (при ≥2) → партия до 4 игроков.**

**Продуктовое решение заказчика (2026-06-19):** старт партии — **хозяин жмёт «Start»**, комната
открыта до 4 мест, начать можно при ≥2 (можно вдвоём или дождаться четверых). НЕ авто-старт по
заполнению. → значит в 2.2.a вводим роль хозяина + кнопку старта (минимально), а не только модель.

**Опора на уже принятые решения** (не переспрашиваем — зафиксировано в ADR):

- **Код комнаты** (ADR-0009): ≥6 символов из криптослучайного non-ambiguous алфавита (≥~30 бит);
  жёсткий rate-limit/лок на неуспешные join (анти-перебор); код НЕ работает после старта/заполнения.
  → Реализуем как **Crockford base32** (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, без I/L/O/U), длина **6**
  = ровно 2^30 = 30 бит. Ввод нормализуем (uppercase + Crockford-декод I→1, L→1, O→0, U→V).
- **Защита памяти** (ADR-0009): TTL + сборка мусора пустых/заброшенных комнат; cap общего числа
  комнат на процесс (graceful-отказ); лимит размера сокет-сообщения; rate-limit на create/join.
- **«Play again» по режиму** (ADR-0014): локально `newGame`; в сети — на сервере (комната жива после
  game:over). Полный реванш тем же составом — это **2.4.b**; в 2.2.a минимум = в онлайне кнопка ведёт
  в меню (выход из партии), а не дёргает локальный `NEW_GAME` (его сервер всё равно denied).
- **Платформа vs игра** (ADR-0011): коды/хозяин/лобби — игро-НЕзависимая платформа (`server/platform`,
  `src/platform`), не лезем в `core`/`render3d`/`sound`.

## Под-шаг 2.2.a-1 — СЕРВЕР + ПРОТОКОЛ (кодим первым)

**Цель:** сервер умеет создавать комнату с кодом, пускать по коду до 4 игроков, держать роль хозяина,
рассылать состав лобби, стартовать партию по команде хозяина (≥2), и защищён от перебора кодов и от
переполнения памяти. Клиентский UI — в a-2; **браузерный онлайн между a-1 и a-2 временно нерабочий**
(клиент 2.1 шлёт старый формат) — это нормально, живая проверка a-1 идёт серверным node-скриптом.

### Файлы (тронем)

- `shared/protocol.ts` — **аддитивно** (старые имена/типы НЕ ломаем, чтобы клиент 2.1 компилировался):
  `PROTOCOL_VERSION` 2→3; новые сообщения `room:create`, `room:start`, `room:lobby`, `room:already-started`;
  новые payload-типы (`LobbyPayload`, `StartRequest`); расширить опц. полями `JoinRequest(+code?)`,
  `JoinedPayload(+code?, +isHost?)`.
- `server/platform/codes.ts` — **НОВЫЙ**: генерация кода (Crockford base32, длина 6, `node:crypto`),
  нормализация ввода, проверка уникальности через переданный «занят ли код» (без коллизий).
- `server/platform/codes.test.ts` — **НОВЫЙ**: длина/алфавит/энтропия, нормализация (I/L/O/U), регенерация
  при коллизии.
- `server/platform/seating.ts` — `Seat += isHost`; `Room += code, createdAt`; чистые хелперы:
  `lobbySnapshot(room)`, `transferHost(room)` (минимальное наследование при выходе хозяина), `canStart(room)`.
- `server/platform/seating.test.ts` — на новые хелперы (host/lobby/canStart/transfer).
- `server/platform/realtime.ts` — реестр комнат **по коду**; обработчики `create`/`join(by code)`/`start`;
  `ROOM_CAPACITY` 2→4; **убрать авто-старт-при-2** (старт только по `room:start` от хозяина);
  rate-limit/лок на неуспешные join (анти-перебор); TTL + cap общего числа комнат; рассылка `room:lobby`
  на изменения состава; сохранить reclaim по `playerId` (2.1.e-2) уже в комнатах-по-коду;
  `maxHttpBufferSize` (лимит размера сообщения).

### Файлы (НЕ трогаем)

- Весь `src/` (клиент) — протокол меняем аддитивно, поэтому компилируется; UI — в a-2.
- `server/index.ts` (сигнатура `attachRealtime` та же), `server/platform/rooms.ts` (применение действий
  не меняется), `server/platform/rng.ts` (значения костей), `core/`, `render3d/`, `sound/`.

### Модель / контракты (что меняется)

- Комната: `{ id=code, code, createdAt, seats: Seat[], game: RoomState|null }`; `Seat += isHost`.
- Реестр: `Map<code, Room>` (был по `roomId`).
- Протокол v3: `create→joined(isHost:true,code)`; `join{code}→joined | not-found | full | already-started`;
  `lobby{code,players[{seat,name,isHost}],capacity,canStart}` (рассылка до старта); `start→state` (всем).

### Граничные случаи

- Коллизия кода при генерации → регенерить (лимит попыток, иначе graceful-ошибка).
- Join по несуществующему коду → `room:not-found` + инкремент счётчика неудач (лок при превышении).
- Join в полную (4/4) → `room:full`; join в идущую партию → `room:already-started` (код мёртв).
- `start` не от хозяина / при <2 / когда партия уже идёт → игнор (или denied), без падения.
- Хозяин вышел из лобби до старта → `transferHost` следующему; если никого живого — удалить комнату.
- Reclaim при реконнекте (по `playerId`) работает в комнате-по-коду (как 2.1.e-2).
- Cap комнат на процесс достигнут → новый `create` отвечает graceful-отказом (не падаем).
- TTL: заброшенная (все сокеты null или пустая) комната подметается; код после этого → not-found.

### Как проверим (живьём, с артефактом)

- `npm run test` — серверные юнит-тесты (codes/seating/rooms) зелёные (вывод).
- `npm run build` + `npm run lint` — сборка клиента (протокол аддитивен) и сервера + линт зелёные (вывод).
- **Живой прогон (артефакт):** временный node-скрипт (`tsx`) с двумя `socket.io-client`:
  client1 `create` → получает код → client2 `join{code}` → оба получают `lobby` → client1 `start` →
  оба получают `state` → client1 `ROLL` → новый `state`. Привести лог. + негатив: `join` по мусорному
  коду → `room:not-found`. (Браузерная живая проверка всего цикла — в a-2.)

### Аудит code-reviewer (2.2.a-1) — итог

Блокеров CRITICAL нет. **Закрыто в a-1 по аудиту:**

- **#5** grace-период на снос ИДУЩЕЙ партии (`emptiedAt` + `GAME_GRACE_MS`) — общий блип сети у всех
  игроков больше не теряет активную партию мгновенно; реальный снос делает sweeper по истечении паузы.
- **#1/#6** reclaim гейтится по `room.game !== null` (в лобби места не держатся) — нет подсадки/захвата
  места в лобби по чужому `playerId`.
- **#2** счётчик перебора `failJoin` растёт на ЛЮБОМ неуспешном join (not-found/already-started/full) —
  не даём оракул «код существует».
- **#7** перегрузка реестра кодов логируется (не проглоченный catch).

## Под-шаг 2.2.a-2 — КЛИЕНТ: функциональный онлайн-цикл (кодим следующим)

**Цель:** вернуть рабочий онлайн в браузере на новом протоколе v3. Полный цикл двумя вкладками:
«Play online» → выбрать Create или Join (ввод кода) → попасть в лобби (код + список + роль) →
хозяин жмёт Start → партия (как в 2.1). Дизайн — переиспользуем классы Вехи 1; красота — a-3.

**Решение по объёму:** a-2 — единый вертикальный срез (проводка + экраны), т.к. живьём проверяется
только целиком (проводка без экранов в браузере не проверить). Крупновато (~9 файлов), но атомарно.

### Файлы (тронем)

- `src/platform/net.ts` — `createOnlineSession(intent, callbacks)`: `intent = {type:'create',name?} |
{type:'join',code,name?}`. На `connect` шлёт `create`/`join` (или reclaim, если уже есть playerId+code).
  Колбэки: `onStatus`, `onLobby(LobbyPayload)`, `onJoined({playerId,seat,isHost,roomId})`. Новые статусы
  `notFound`/`alreadyStarted`. Сессия += метод `start()` (emit `room:start`) — старт сессионный, не игровой.
- `src/transport/NetworkTransport.ts` — конструктор берёт `intent` вместо `roomId`; на `connect` шлёт
  create/join по intent (reclaim при playerId+code); хранит `code` (для create узнаёт из `joined`).
  Игровой канал (action/state/denied/pending/playerId) — без изменений.
- `src/transport/NetworkTransport.test.ts` — обновить под новую сигнатуру конструктора (intent).
- `src/state/gameStore.ts` — `goOnline(intent)`; новые поля `lobby`/`mySeat`/`isHost`/`roomCode`;
  `startGameOnline()` → `session.start()`; проводка колбэков net; `goLocal` сбрасывает новые поля.
- `src/state/gameStore.test.ts` — обновить (goOnline(intent) + фейк-сессия с lobby/start).
- `src/ui/screens/OnlineScreen.tsx` — переписать в «онлайн-вход»: кнопки Create / Join, поле кода (для
  join), опц. поле имени; по действию `goOnline(intent)`; показ статуса (connecting/offline/notFound/
  full/alreadyStarted). Переиспользуем `start__panel`/`field-label`/`back-link`.
- `src/ui/screens/LobbyScreen.tsx` — **НОВЫЙ**, функциональный: код комнаты (крупно), список игроков
  (имя + бейдж host + «you» по `mySeat`), кнопка **Start** (только хозяину, disabled пока `!canStart`),
  «← Leave» (`goLocal`). Классы — `players`/`player-row`/`back-link` из StartScreen.
- `src/App.tsx` — роутер += Lobby: `mode==='online' && lobby && !state` → `<LobbyScreen/>`.
- `src/ui/theme.css` — минимум новых классов под лобби (код/бейджи), если не хватит существующих.

### Файлы (НЕ трогаем)

- `shared/protocol.ts` (готов в a-1), весь `server/`, `core/`, `render3d/`, `sound/`, `MenuScreen.tsx`
  (его «Play online» уже ведёт в OnlineScreen), `uiStore.ts` (лобби определяется ДАННЫМИ `lobby!=null`,
  отдельный вид не нужен).

### Граничные случаи / решения

- Имя игрока: в a-2 опциональное поле (сервер уже чистит `cleanName`, анти-XSS). Полная валидация
  (NFC/bidi/zod) — 2.2.b. Без имени сервер даёт «Player N».
- Реконнект в лобби: место не держится (a-1) → при возврате fresh-join (новый seat). Приемлемо.
- «you» в списке — по приватному `mySeat` (из `joined`), НЕ по playerId (его чужих клиент не знает).
- Старт переводит в партию по приходу `state` (роутер): LobbyScreen размонтируется сам (как OnlineScreen).
- Краевые статусы (not-found/full/already-started) в a-2 — простой текст; понятные экраны — a-3.

### Как проверим (живьём, с артефактом)

- `npm run test` (обновлённые NetworkTransport/gameStore + остальные) + `npm run build` + `npm run lint` —
  вывод зелёный.
- **Браузер, две вкладки** (`npm run dev:all`): вкладка1 Create → код; вкладка2 Join по коду → обе видят
  лобби с составом; хозяин Start → у обоих партия; ход/бросок ходят по сети. Скриншот/лог + описание.
  Негатив: Join по мусорному коду → видимый статус ошибки.

### Аудит code-reviewer (2.2.a-2) — итог

1 CRITICAL + 2 MAJOR закрыты в a-2:

- **#1 (CRITICAL)** наследование хозяина не доходило до клиента: Start гейтился по store-полю `isHost`
  из `joined`, а сервер при выходе создателя шлёт только новый `room:lobby` (без нового `joined`) →
  промотированный игрок не видел Start, лобби «залипало». Фикс: `LobbyScreen` берёт роль из СВЕЖЕГО
  состава (`lobby.players[mySeat].isHost`).
- **#2 (MAJOR)** реконнект в лобби терял имя → пробрасываем `name` в reclaim-join (`NetworkTransport.enter`).
- **#3 (MAJOR)** после ошибки входа нельзя было повторить (только «Back to menu») → кнопка «Try again»
  (`goLocal` → форма; код/имя сохранены в локальном стейте экрана).

Подтверждено корректным: анти-воскрешение сессии при goLocal/reset (поля чистятся, поздние эмиты глушатся);
роутер state>lobby>форма; границы ADR-0011 (UI/transport в ядро не лезут).

## Хвосты / спящие баги (в backlog при закрытии фичи)

- **Rate-limit и лимит комнат по IP/сессии** (ADR-0009, аудит #3/#4): сейчас анти-перебор/анти-спам —
  per-socket (сбрасывается реконнектом) + энтропия кода 30 бит. Агрегация по IP/identity (connect/create/
  join), переживающая реконнект, + trust-proxy на Railway — отложена до появления identity (2.2.b/2.4).
- **Reconnect-токен на место вместо публичного `playerId`** (ADR-0010, 2.4.c): reclaim сейчас по `playerId`
  (унаследовано от 2.1.e-2); гейт по идущей партии сужает поверхность. Непубличный токен — в 2.4.c.
- **Интеграционный socket-тест `realtime.ts`** (аудит #10): покрыты чистые модули (codes/seating) + живой
  smoke; регресс-тест путей reclaim/наследование хозяина/grace-снос/оракул — кандидат (созвучно хвосту 2.1).
- **Длина `actionId` не ограничена** в `isActionMessage` (rooms.ts) — рост `processed[]` (аудит #8). MINOR.
- **`room:full` с `roomId:''` = «сервер перегружен»** — отдельный reason vs «комната занята» (аудит #9):
  различить в UI/протоколе в 2.2.a-3.
- **Роль хозяина теряется при реконнекте в ЛОББИ** (аудит a-2 #2): место в лобби не держится → fresh-join
  с `isHost:false`. Имя сохранили, роль — нет. Полное наследование/удержание — 2.2.c (+reconnect-токен 2.4.c).
- **Метка `waiting`='Joining room…'** после состоявшейся посадки до прихода `room:lobby` (аудит a-2 #4) —
  семантика метки/полировка статусов: 2.2.a-3.
- **`aria-live` первого статуса** входа не озвучивается (узел появляется уже с текстом, аудит a-2 #6) —
  a11y-полировка экранов входа/лобби: 2.2.a-3.
