# 2.4-leaderboard (фича в roadmap: Веха 2 → 2.4 Лидерборд + реконнект-арбитраж + полировка)

Последний коммит по фиче: d27f53f (2.4.c-1, протокол v5 — НЕ на проде, выкатим со всей 2.4.c). ПРОД сейчас на v4: 2.4.a задеплоена + лидерборд засеян синтетикой (railway up 340baca, 2026-06-21)
Файлы под-шага c-2 (тронем): server/platform/{seating,rooms,realtime}.ts, server/platform/stats/onGameOver.ts, docs/adr/{0009,0018}, + тесты rooms/seating/onGameOver. НЕ трогаем: shared/**, src/** (клиент/ядро), протокол остаётся v5.

> Решения (заказчик 2026-06-21, ADR-0018): лидерборд — публичная таблица; **сортировка по СУММЕ
> очков**; строка богатая: ник+аватар · очки(сумма) · лучшая игра(max) · сыграно · победы. Зачёт —
> только честные СЕТЕВЫЕ партии с ≥2 РАЗНЫМИ зарегистрированными (`matches.registeredCount>=2`),
> гостевые/брошенные/локальные — нет. Удалённые аккаунты в витрине не показываем. Анти-фарм — мягко
> для пилота (риск сговора задокументирован, строгая защита → backlog). Приватно: только ник+аватар+
> метрики. Новый экран из меню + ссылка из кабинета.
>
> Данные ГОТОВЫ (2.3.d): `matches`/`match_players` пишутся; лидерборд = запрос+экран, без миграции.
> Реванш (бывш. 2.4.b) — уже сделан в 2.5. Кросс-секционное требование (англ-строки, a11y, состояния
> загрузка/пусто/ошибка, мобайл) — планка КАЖДОГО нового экрана.

  - [~] **c-2 — таймер дропа + форфейт-добивание (БЕЗ протокола, чистая серверная логика)** — В РАБОТЕ (код, не закоммичен):
    Поведение (продакт): соперник вышел и не вернулся за ~60с → сервер доигрывает за него на автопилоте, партия
    ГАРАНТИРОВАННО доходит до конца (`game:over`), оставшиеся видят итог (а не вечное «ждём»). Такая партия НЕ
    идёт в рейтинг (форфейт). В партии 1-на-1 это значит: оставшийся доигрывает свои ходы сам, ушедший — авто;
    как только обе карточки заполнены — экран победителя.
    **Тронем (только сервер + docs + тесты):**
    • server/platform/seating.ts — `Seat.disconnectedAt:number|null`, `Room.forfeited:boolean`; сброс
    `forfeited`/`disconnectedAt` в `resetRoomToLobby`, init в `createHouseTables`.
    • server/platform/rooms.ts — чистая `applyForfeitTurn(module, room, actorId, rollValues)`: один авто-ход
    ROLL(CSPRNG)→SCORE в первую свободную (`availableCategories[0]`), server-minted actionId; идёт через
    тот же путь версий/идемпотентности. Тестируема без сокетов.
    • server/platform/realtime.ts — disconnect-ветка: ставим `disconnectedAt=Date.now()` при socketId→null
    in-game; обе reclaim-ветки (join/joinOpen): чистим `disconnectedAt=null`; init полей в create/addSeat;
    sweeper game-ветка: детект «current отсутствует > таймаута» → каскад; после успешного `MSG.action`:
    до-промотка; общий `runForfeits(room)` — крутит каскад, ставит `forfeited`, шлёт `MSG.state`, гейтит запись.
    • server/platform/stats/onGameOver.ts — параметр `forfeited`; `true` → `return null` (не пишем/не рейтингуем).
    • docs/adr/0009 (§форфейт: автозапись в первую свободную) + 0018 (§1: форфейт-партии вне рейтинга/истории).
    • Тесты: rooms (applyForfeitTurn доводит до game:over; каскад «оба вышли»), onGameOver (forfeited→null),
    seating (сброс полей в reset).
    **НЕ трогаем:** shared/protocol.ts, shared/schemas.ts, src/core/** (используем готовые `availableCategories`/
    `reduce`/`isGameOver`), весь клиент src/** — оверлей «ждём {имя}…» и терминал «партия завершена» это c-3;
    протокол НЕ меняется (остаётся v5) → новой прод-несовместимости c-2 не вносит.
    **Механика `runForfeits(room)`:**
    • ход-форфейт, если `state.current` — место с `socketId===null` И `now-disconnectedAt > FORFEIT_MS` (~60с);
    • за такого: `applyForfeitTurn` (actorId = playerId места); `reduce` сам передаёт ход / ставит `game:over`;
    • цикл: повторяем, пока следующий current тоже отсутствует+просрочен (промотка нескольких ушедших «разом»),
    стоп на ЖИВОМ игроке или `game:over`; ставим `room.forfeited=true`, шлём один `MSG.state` с накопл. событиями;
    • зовём из (1) sweeper-тика (таймер дропа — гарантирует завершение) и (2) обработчика `MSG.action` после
    успешного хода живого (чтобы не ждать 60с на каждом круге отсутствующего — «не держать 13 минут», C3-фикс).
    **Граничные случаи / гонки:**
    • «оба/все вышли»: каскад из sweeper доигрывает до `game:over` за один тик; FORFEIT_MS(60с) < GAME_GRACE_MS(120с)
    → форфейт срабатывает раньше grace-сноса; после game:over обычная ветка снесёт (private) / reset (persistent).
    • вернулся в окне: reclaim уже обнулил `disconnectedAt` → каскад его не трогает (атомарно — Node однопоточный).
    • идемпотентность: авто-ход идёт через `processed[]`/версии как обычное действие; двойного тика нет; каскад
    читает СВЕЖИЙ state на момент срабатывания (m1).
    • C1-фикс (BLOCKING): любое авто-добивание ⇒ `room.forfeited=true` ⇒ `onGameOver` вернёт `null` ⇒ в `matches`
    ничего, рейтинг не трогаем (ADR-0018). Тест: дроп-до-конца → 0 строк в `matches`; зависания нет.
    **Живая проверка:** подниму сервер локально, 2 вкладки → старт партии → закрываю одну → жду форфейт-таймаут
    (на время теста временно уменьшу FORFEIT_MS) → у оставшейся вкладки появляется экран победителя (`game:over`
    пришёл) + в логе сервера «forfeit», recordMatch не пишет/вернул null. Плюс юниты на гейт записи и каскад.
    **Размер:** уложился в один под-шаг (~150 строк кода + тесты), дробить не понадобилось.
    **CHECK (done):** typecheck:server ✓, 248 тестов ✓, lint ✓, full build ✓. ЖИВОЙ прогон (реальные сокеты,
    локальный сервер, FORFEIT_MS временно 2с): старт партии → оба вышли → сервер за ~2.5с доиграл форфейтом →
    лог «game finished by forfeit — not recorded (ADR-0018)» (прогнал дважды — до и после фикса аудита).
    Независимый аудит (code-reviewer): **1 MAJOR ПОЧИНЕН** — `actionId` форфейта был детерминирован
    (`forfeit-<версия>`), клиент мог заранее засеять `processed[]` (даже denied-ход пишет actionId) → авто-ход
    `duplicate` без смены версии → каскад завис бы навечно. Фикс: `applyForfeitTurn` принимает `mintActionId`,
    realtime передаёт `randomUUID` (НЕугадываемый); `runForfeits` делает `break` на denied/duplicate и метит
    `forfeited` только при применённом ходе. Регресс-тест добавлен (повтор id → score=duplicate).
    Уточнения по факту (MINOR, приняты): шлём `MSG.state` НА КАЖДЫЙ авто-ход (а не один на каскад) — версионно
    валидно, клиент видит ходы автопилота; реальный таймаут форфейта 60–120с (гранулярность sweeper-тика 60с) —
    в пределах ADR-0010, UX-оверлей закроет c-3.

## Хвосты / спящие баги (учесть/отложить)

- **Строгий анти-фарм лидерборда** (кулдаун зачёта повторных встреч пары, детект сговора,
  уникальность по IP/identity) — backlog, ДО широкого запуска (ADR-0018; вектор из аудита 2.5).
- **Сортировка/пагинация лидерборда** — старт: топ-N по сумме очков. Кликабельные колонки/страницы — позже.
- **`/leaderboard` без rate-limit/кэша** (публичный GET, как `/tables`/`/status`) — общий хвост лимитов.
- **Заметка гостю «результат не в рейтинге»** (перенос из 2.2.b) — показать на экране входа/итогов гостю.
- Реклейм-токен (c) закрывает: 32-битный `playerId` (аудит 2.5), удержание хозяина (2.2), «застрявший
  ход отсутствующего» (2.1/2.2) — свести при реализации c.
