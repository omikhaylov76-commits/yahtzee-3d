## Веха 2 — Сетевая игра + кабинеты + лидерборд

merged: —

> Архитектура спроектирована (ADR 0007–0014 + раздел «Сетевая игра» в architecture.md).
> Стек: Node + Socket.IO + PostgreSQL на Railway. Авторитетный сервер переиспользует `core/`,
> ядро НЕ переписываем. Вход: Google + гость. Без оверинжиниринга на старте — просто и расширяемо.
>
> **Сеть строим как переиспользуемую платформу** (ADR-0011): Yahtzee — первый «модуль игры»,
> сетевое (комнаты/вход/кабинеты/лидерборд) отделено от игро-специфичного чистым швом
> (контракт `GameModule`), чтобы потом подключить вторую игру (портал — Веха 4+). Без
> оверинжиниринга: реализуем только нужное Yahtzee.
>
> Путь игрока: вход (Google или гость) → [кабинет, если зарегистрирован] → создать/войти в
> комнату по коду → собрались 2–4 → игра по сети → результат в статистику/лидерборд.

**Порядок намеренный:** сначала сервер заработает по сети между двумя вкладками (каркас +
realtime + `NetworkTransport`), потом комнаты с кодами, потом вход Google + кабинеты, потом
лидерборд, потом полировка реконнекта. Сетевую игру (2.1) можно щупать раньше аккаунтов.

> **Правки по двум раундам аудита (ADR 0012–0014 добавлены).** Снято 6 мест, где план ломался:
> ① античит-RNG — `mulberry32` предсказуем по выходам → значения костей из серверного **CSPRNG**
> (ADR-0012); ② **версия состояния + идемпотентность + фазы хода** от сервера (ADR-0013) — иначе
> рассинхрон/двойные действия/разблокировка по анимации; ③ **ядро ДОПОЛНЯЕМ** (внешние id +
> инъекция значений + `GameModule`-функции); ④ **сборка сервера** — вторая цепочка (раннер/ESM/
> engines), решить ДО 2.0; ⑤ **режим local↔online + меню + развод localStorage + соло-рекорд**
> (ADR-0014); ⑥ **код комнаты/лимиты/реконнект-арбитраж**. Наблюдатели — backlog.

> **Кросс-секционное требование (как в Вехе 1, НЕ в хвост):** ВСЕ новые сетевые экраны (меню,
> лобби, кабинет, лидерборд, вход) делаем сразу с английскими строками вне логики, базовой a11y
> (клавиатура/фокус/aria), состояниями загрузка/пусто/ошибка и мобильным адаптивом. Это не
> отдельный под-шаг «потом», а планка качества каждого экрана.

### Масштаб 300–500 и тарифы Railway (ориентир, проверить цены перед запуском)

Стек к этому готов **без переписывания** (ADR-0007/0009). Узкое место — **НЕ БД** (она вне
горячего пути: запись раз в конце партии, чтения кэшируемы), а **RAM/CPU одного сервера**
(websocket-соединения + комнаты в памяти) и лимит «один процесс». Доращивание: несколько
копий сервера + Redis-шина (комнаты независимы) — поздний шаг, на старте не делаем.

| Нагрузка           | Что нужно                                            | Грубо в месяц          |
| ------------------ | ---------------------------------------------------- | ---------------------- |
| ~10 игроков        | 1 маленький сервер + маленький Postgres              | ~$5–10 (уровень Hobby) |
| ~100 (~30 комнат)  | 1 сервер 0.5–1 ГБ RAM + Postgres                     | ~$10–25                |
| ~500 (~150 комнат) | 1 сервер 1–2 ГБ RAM (или 2 копии + Redis) + Postgres | ~$25–60                |

> Railway берёт по факту потребления (RAM/CPU/трафик), не фиксировано. Серьёзные деньги — только
> вместе с серьёзным числом живых игроков.

### Главные риски Вехи 2 и как закрываем

- **Синхронизация** → авторитетный сервер: единственный источник правды — он, клиенты проигрывают
  (ADR-0009). Низкий риск.
- **Отключения/реконнект** (мобильный интернет) → самое каверзное: пауза «ждём» + перезаход по
  токену/коду + таймаут на выход (ADR-0010); Socket.IO помогает с авто-reconnect.
- **Безопасность** → секреты только в переменных окружения Railway; проверка каждого действия на
  сервере; ограничение частоты; вход через Google (паролей не храним, ADR-0008).
- **Накрутка рейтинга** → в лидерборд только заверенные сервером итоги сетевых партий с людьми,
  анти-фарм и анти-спам (ADR-0009, 2.4.a).
- **Потеря партий при рестарте сервера** (состояние в памяти) → для дружеских партий приемлемо;
  устойчивость к рестартам — возможное улучшение позже (отмечено в ADR-0009).

## Backlog / хвосты

- **Наблюдатели/зрители в комнате** — отложено из Вехи 2 (решение заказчика: 2–4 друга, лишняя
  сложность). Кандидат на Веху 4+ (портал) или отдельную фичу: возможность зайти 5-м смотреть.
- **Горизонтальное масштабирование сети** (когда дорастём): несколько копий сервера + Redis-шина,
  а также **sticky-routing** комнаты к процессу (клиент должен попадать на процесс со своей комнатой)
  — заложено как возможность в ADR-0007/0009, на старте один процесс, не делаем.
- **Устойчивость сетевых партий к рестарту/деплою сервера** — сейчас состояние в памяти, рестарт
  роняет активные партии (ADR-0009, приемлемо для дружеских). Аккуратный drain / персистентность
  активной партии — возможное улучшение позже.
- **Анти-фарм лидерборда от сговора** — на старте ловим только случайное; защита от двух
  сговорившихся аккаунтов (уникальность по аккаунту/IP, детект пар) — отдельная задача позже (2.4.a).
- **ЗВУК НЕ ФИНАЛЬНЫЙ.** Сейчас стоит временный процедурный звук (Web Audio, ADR 0006) — это
  заглушка. Заказчик ПОЗЖЕ доделает звук полноценно: подберёт и подключит качественные реальные
  сэмплы (стук костей, клики, фанфары и т.д. — Kenney / freesound, CC0) за тем же интерфейсом
  `SoundEngine`. Архитектура специально оставлена открытой под замену звука без переписывания.
  Это запланированное будущее улучшение — дверь оставлена открытой.
- reduced-motion + 3D: РЕШЕНО (F6.3 + правка по фидбэку). 3D-бросок — игровая механика, а не
  декор: кости катятся ВСЕГДА, независимо от системного reduce-motion. Reduce-motion гасит только
  декоративное (фейды экранов, частицы Yahtzee, пульс очков, glow). Ранняя гипотеза «мгновенный
  бросок при reduce» отменена: пользователь с включённым reduce хочет видеть бросок.
- Физику падения костей «попилить» позже: дошлифовать кувырок в воздухе/качение по столу и
  естественность доводки на грань (детерминированная доводка предсказателя — местами можно
  натуральнее). Базовое поведение принято заказчиком (F4).
- Бандл ~3 МБ (Three.js + Rapier WASM) — РЕШЕНО в F6.4: 3D-арена вынесена в ленивый чанк, старто-
  вый JS ~174 КБ. Сам 3D-чанк остаётся крупным (Three+Rapier WASM ~2.9 МБ) — грузится по требова-
  нию; дальнейшее дробление three/rapier — при желании позже, выгода невелика.
- a11y: фиксация костей в 3D — только указателем (клик), без клавиатуры. 2D-fallback (Die как
  button) с клавиатуры работает; sr-only статус значений есть. Полноценный keyboard-hold для 3D —
  отдельная фича (перенесено из F6.3).
- 60fps: проверка в DevTools Performance — на заказчике (ленивая загрузка на рантайм-fps не влияет).
- 5 npm-уязвимостей в транзитивных dev-зависимостях — проверить `npm audit`, закрыть без

- Джокер: строгое принуждение бокса (сначала верхний по достоинству) не enforced в ядре —
