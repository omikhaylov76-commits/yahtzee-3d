## Веха 2 — Сетевая игра + кабинеты + лидерборд

merged: —

> Архитектура спроектирована (ADR 0007–0014 + раздел «Сетевая игра» в architecture.md).
> Стек: Node + Socket.IO + PostgreSQL на Railway. Авторитетный сервер переиспользует `core/`,
> ядро НЕ переписываем. Вход: Google + гость. Без оверинжиниринга на старте — просто и расширяемо.
>
> **Сеть строим как переиспользуемую платформу** (ADR-0011): Yahtzee — первый «модуль игры»,
> сетевое (комнаты/вход/кабинеты/лидерборд) отделено от игро-специфичного чистым швом
> (контракт `GameModule`), чтобы потом подключить вторую игру (портал — Веха 4+). Без
> оверинжиниринга: реализуем только нужное Yahtzee.
>
> Путь игрока: вход (Google или гость) → [кабинет, если зарегистрирован] → создать/войти в
> комнату по коду → собрались 2–4 → игра по сети → результат в статистику/лидерборд.

**Порядок намеренный:** сначала сервер заработает по сети между двумя вкладками (каркас +
realtime + `NetworkTransport`), потом комнаты с кодами, потом вход Google + кабинеты, потом
лидерборд, потом полировка реконнекта. Сетевую игру (2.1) можно щупать раньше аккаунтов.

> **Правки по двум раундам аудита (ADR 0012–0014 добавлены).** Снято 6 мест, где план ломался:
> ① античит-RNG — `mulberry32` предсказуем по выходам → значения костей из серверного **CSPRNG**
> (ADR-0012); ② **версия состояния + идемпотентность + фазы хода** от сервера (ADR-0013) — иначе
> рассинхрон/двойные действия/разблокировка по анимации; ③ **ядро ДОПОЛНЯЕМ** (внешние id +
> инъекция значений + `GameModule`-функции); ④ **сборка сервера** — вторая цепочка (раннер/ESM/
> engines), решить ДО 2.0; ⑤ **режим local↔online + меню + развод localStorage + соло-рекорд**
> (ADR-0014); ⑥ **код комнаты/лимиты/реконнект-арбитраж**. Наблюдатели — backlog.

> **Кросс-секционное требование (как в Вехе 1, НЕ в хвост):** ВСЕ новые сетевые экраны (меню,
> лобби, кабинет, лидерборд, вход) делаем сразу с английскими строками вне логики, базовой a11y
> (клавиатура/фокус/aria), состояниями загрузка/пусто/ошибка и мобильным адаптивом. Это не
> отдельный под-шаг «потом», а планка качества каждого экрана.

### Главные риски Вехи 2 и как закрываем

- **Синхронизация** → авторитетный сервер: единственный источник правды — он, клиенты проигрывают
  (ADR-0009). Низкий риск.
- **Отключения/реконнект** (мобильный интернет) → самое каверзное: пауза «ждём» + перезаход по
  токену/коду + таймаут на выход (ADR-0010); Socket.IO помогает с авто-reconnect.
- **Безопасность** → секреты только в переменных окружения Railway; проверка каждого действия на
  сервере; ограничение частоты; вход через Google (паролей не храним, ADR-0008).
- **Накрутка рейтинга** → в лидерборд только заверенные сервером итоги сетевых партий с людьми,
  анти-фарм и анти-спам (ADR-0009, 2.4.a).
- **Потеря партий при рестарте сервера** (состояние в памяти) → для дружеских партий приемлемо;
  устойчивость к рестартам — возможное улучшение позже (отмечено в ADR-0009).

## Монетизация — заявленная цель (строим ПОЗЖЕ; фундамент закладываем по ходу Вехи 2)

Заказчик строит пилот как основу под РАЗВИВАЕМЫЙ монетизируемый продукт (не разовая игра с друзьями).
Сейчас механику оплаты НЕ строим — фиксируем цель и принцип, чтобы решения Вех 2–3 её не подрезали
(зафиксировано 2026-06-20).

- **Принцип (РЕШЕНО): no pay-to-win.** Монетизируем красоту и удобство, НЕ игровое преимущество — иначе
  рушится честный лидерборд (авторитетный сервер). Оформить мини-ADR при старте лидерборда (2.4.a).
- **Модель — НЕ выбрана** (решаем у кабинетов 2.3.d, там впервые влияет на код): подписка / косметика
  (скины костей, темы стола) / реклама (только rewarded) / премиум-функции хоста / battle pass / донат /
  турниры (ТОЛЬКО косметические призы — денежные = юр-риск азартных игр). Рекомендация: косметика + подписка.
- **Крючок в фундамент (2.3.a/d):** в модели аккаунта заранее заложить нейтральные поля «тариф (tier)» +
  «владения (entitlements)» — пустые полочки под любую модель без миграции БД потом.
- **Приватность/согласие (ДОПОЛНЕНО к 2.3.d):** под регистрацию + сбор статистики — минимальная политика
  конфиденциальности + согласие пользователя; логи без PII/токенов (уже в 2.3.d). Для монетизации обязательно.
- **Свой домен** (вместо …railway.app) — для доверия; ручное действие, когда выйдем из стадии теста.
- **Платежи** (Stripe/ЮKassa) + юр.лицо/самозанятость — отдельный крупный пласт, отдельной вехой, когда
  будет аудитория и выбрана модель.
